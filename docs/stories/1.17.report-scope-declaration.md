Umbrella: https://github.com/tim-nish/kogaki/issues/70. On conflict, the
umbrella issue and `specs/SPEC.md` §4 clause 5 win.

As the Kogaki repository owner, I want a review report to state whether it is a
full or a delta review, so that the merge layer stops trusting an assurance
nobody made and round 2 stops paying to re-derive round 1.

## Context

`specs/SPEC.md` §4 clause 5 is this story's governing text, added in the same
sitting under kogaki#70's alternative A. The measurement is primary capture from
PR #67's own route logs: round 2 ran **43 turns to round 1's 37** and repeated
nearly all of it — PR view, issue view, full diff, registry diff, receipts check.

**The declaration is the load-bearing half, not the delta.** Clause 1's
mechanical half reads *report present ∧ no open blocking findings* identically
whatever the round, so it cannot distinguish a full review from a delta one. A
delta review is the right economics; an *undeclared* delta review is a narrower
assurance wearing a full review's clothes.

## Acceptance criteria

1. **Given** a review report is composed, **when** it is posted, **then** its
   body carries a scope declaration — `full` or `delta` — in a fixed,
   machine-findable form, beside the `review-lane report: <sha>` token that
   `.claude/skills/review-lane/SKILL.md:178` already fixes.

2. **Given** a report carries no scope declaration, **when** it is read,
   **then** it is read as `full` — the compatibility direction §4 clause 5
   states, so the reports already in this repository's history are not
   retroactively narrowed.

3. **Given** a round-2 review, **when** its scope is determined, **then** the
   default is `delta`: round 1's findings × the fix commits, verifying each
   finding resolved and reviewing only the diff the fix introduced.

4. **Given** a fix touched files **outside** the files round 1's findings named,
   **when** round 2 scopes itself, **then** it escalates to `full` for the
   diff and declares `full`. The delta is a default, never a ceiling.

5. **Given** the round-1 report exists and is segment-bound to its head,
   **when** round 2 runs, **then** it reads that report as its input rather
   than reconstructing round 1's observations from the PR.

## Story questions

- **Does the scope declaration belong on the report line or its own line?**
  The presence token is matched by a fixed regex
  (`tools/review-sweep.sh` `REPORT`), and widening that regex risks the
  use-vs-mention class kogaki#41 already fixed once. **Unverified — the
  interaction between a widened report line and the existing segmentation was
  not traced this sitting.** A separate adjacent line is the conservative
  option; confirm against the segmenter before choosing.

## File boundaries

Touches `.claude/skills/review-lane/SKILL.md` and, if the declaration is
parsed rather than merely written, `tools/review-sweep.sh`'s segmenter and
`checks/check-review-report.sh`. **Accepted overlap:** story 1.19 also edits
`tools/review-sweep.sh`. Scheduling edge, never a `depends_on`.
