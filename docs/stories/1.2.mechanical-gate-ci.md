As the Kogaki repository owner, I want the mechanical gate half SPEC §4
declares to actually fire, so that a guard nothing invokes stops being
indistinguishable from no guard.

## Context

`specs/SPEC.md` §4 declares the mechanical half "runs unconditionally in
CI/hooks" and the registry meta-check exists
(`checks/check-registry-conformance.sh`, admitted at
`checks/registry.json` with tier `pre-push`), but nothing invokes it — no
CI workflow, no git hooks, no suite runner (enumeration in kogaki#6's
`searched:` line).

## Acceptance criteria

- **Given** a pull request (or push to master), **when** CI runs, **then**
  every check registered in `checks/registry.json` executes, with
  **registry-driven discovery** — the workflow enumerates the registry,
  never a hardcoded list (constraint carried from the registry's own note,
  `checks/registry.json:2-7`: the suite runs only registered checks).
- **Given** a PR adding an unregistered check file, **when** CI runs,
  **then** it fails (the meta-check firing in CI — negative run recorded in
  the PR). (New wiring; the check itself ships: `checks/check-registry-conformance.sh`.)
- **Given** a PR (or push) naming no licensing issue (`#N` in
  title/body/commits), **when** the gate runs, **then** it refuses —
  deny-never-warn — and the output says the work re-routes to an issue
  (contract: `specs/SPEC.md` §4 PR-gate and responsibility clauses;
  negative run recorded).
- **Given** a registry entry whose admission record is empty or missing a
  required field (contract-or-defect, license, tier, removal signal),
  **when** the gate runs, **then** it fails naming the entry and field.
  Lands as a widening of the meta-check under kogaki#6's license or as a
  second registered check — implementer's call; the admission record is
  updated/added either way. (Today an empty admission object passes:
  `checks/check-registry-conformance.sh` compares filenames only.)
- **Given** a clean PR, **when** the gate runs, **then** it passes and its
  output names what it checked.
- Any new or widened check carries its admission record fields per the
  registry note, with the removal signal declared at birth
  (`consulted: product-lab@bb68ccf topics/claude-code-ops.md:19`).

## Story questions

- Whether a local pre-push hook mirrors the CI workflow is optional in the
