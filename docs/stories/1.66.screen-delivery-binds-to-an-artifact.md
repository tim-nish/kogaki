# Story 1.66: Screen delivery binds to an artifact, not to a display channel

## Context

`specs/spec-terrain/SPEC.md` §14.4.1 (v18, owner ruling 2026-08-15, kogaki#434)
rules that an owner-facing screen is delivered as an **artifact the runtime
writes**, never through a display channel. This story builds that ruling.

The defect it closes: §14.4's delivery instructions bound to a tool call's
stdout, which the harness displays to the model and not reliably to the owner.
With retyping prohibited (§14.4), a question UI prohibited after tag selection
(§6.3), and model-side re-emission refused, **every conformant run rendered
nothing** — and the observed result was not silence but a false claim of
success (*"The agents co-tag screen is above"* over a collapsed tool line).

## Scope

Two files carry the change, and the spec is already amended — this story does
not touch `specs/spec-terrain/SPEC.md`.

- **`terrain/terrain.mjs`** — each screen render also writes
  `reports/Screen.md`: fixed name, overwritten per render, joined from the same
  renderings directory `FullReport.md` is joined from, so a second screen name
  is unwritable rather than detected.
- **`.claude/skills/terrain/SKILL.md`** — the §14.4 projection is corrected.
  Its current text (*"the command's own output IS the reply"*, *"run `cat <that
  path>` and let the tool output be what the owner reads"*) instructs delivery
  through the channel §14.4.1 rules against, and is false at this head.

## Acceptance criteria

1. **AC1 — the runtime writes the artifact.** Every screen render writes
   `reports/Screen.md`. The path is joined from the renderings directory with
   the literal `Screen.md`, matching how `FullReport.md` is written, so no
   caller can mint a second screen name.

2. **AC2 — overwritten, never accumulated.** A second render in the same run
   replaces the file. After N renders, `reports/` holds exactly one
   `Screen.md`. This is §12.2 (v12)'s accumulation rule applied to the screen,
   and it is asserted by rendering twice and counting files — not by reading
   the write call.

3. **AC3 — the skill stops instructing a channel, and still requires a
   hand-over.** Two properties, and they are separable — an earlier draft of
   this AC ran them together and contradicted itself in adjacent sentences
   (PR #460 round 1, finding 4):

   - **The projection requires that the artifact be named to the owner** as
     the first act after the command returns. This is §14.4.1's hand-over
     floor; a projection that leaves it optional permits the run that writes
     the file and says nothing, which is the state kogaki#434 was filed
     against.
   - **The projection mandates no particular FORM for that naming.** It must
     not require a pointer, an `!`-command, or a file-send specifically.
     §14.4.1 makes the form non-normative on purpose, and a projection fixing
     one would re-import the harness binding the ruling removed.

   The satisfying shape is an instruction of the form *"name the artifact to
   the owner; how you name it is yours"* — obligation fixed, form free. The
   test for the second half is that the text names at least two acceptable
   forms without ranking them, or names none while still requiring the act.

4. **AC4 — the one-producer rule is visibly intact.** The projection still
   prohibits retyping, summarizing, re-formatting, tabulating and paraphrasing,
   and says why handing over an artifact is not retyping. §14.4 is narrowed,
   not repealed, and a reader of the skill must be able to see that.

5. **AC5 — "delivering nothing is still a failure" survives with a satisfiable
   discharge, and the discharge is the HAND-OVER.** The sentence stays, and the
   projection names what discharges it: naming the artifact to the owner, not
   writing the file. A projection that reads the write as the discharge
   satisfies the clause while producing the failure it names.

## Verification

**AC1 and AC2 are mechanically checkable and owe a mutation, not an
observation.** Render twice into a temporary tree, assert exactly one
`Screen.md` and that its bytes match the second render. Then break the write
path and confirm the assertion fails — a screen test that passes when nothing
is written is the defect class kogaki#243 tracks, and this story is not exempt
from it.

**AC3–AC5 are prose properties of a projection and have no mechanical carrier.**
State that rather than inventing one: the check is a read at review, and the
skill is not covered by `checks/check-terrain-composition.sh`, which reads the
runtime's composition and not the skill's instructions.

## Out of scope

- The delivery mechanism itself. §14.4.1 leaves it non-normative; this story
  must not pick one and must not add a clause that effectively picks one.
- The Full Report's delivery, which §12.2 (v12) already sites correctly.
- Any lint over model output — §14.4's rationale refuses it explicitly, and it
  would re-create the producer the clause removes in order to have something
  to check.
