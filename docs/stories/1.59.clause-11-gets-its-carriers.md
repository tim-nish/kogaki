## Story

As the reviewer reading a successor to a superseded PR, I want the successor's
declared obligations to be visible where I already read the review record — and
the block's own diagnosis to be falsifiable — so that a supersession is a
continuation I can audit rather than a fresh PR that happens to mention an old
one.

## Grounding

- **Governing contract:** `specs/SPEC.md` §4 **clause 11**, ratified 2026-08-11
  (kogaki#306, Owner Rule 2026-08-09). Clause 3 names the supersession lane;
  clause 8 lends the `carried:`/`declined:` grammar. Both point at clause 11
  and neither is reopened here.
- **Clause 11 has NO carrier today.** Every property it states is prose. That
  is the whole of why this story exists, and it is the condition to check
  against at pickup rather than assume.
- **What already exists, read not inferred:** `tools/review-sweep.sh` computes
  the `supersede` state in `decide()` (`return 'supersede'`, ~`:3097`) and the
  driver announces it on the PR naming every finding the successor owes a
  disposition for. Its own header states what it does **not** do: no
  `gh pr create`, no `pr close`, no fixer spawn.
- **Where the obligation half attaches:** `checks/check-review-report.sh` owns
  the review-record grammar, clause 8's dispositions, and the `done` boundary
  that already prints open non-gating findings carrying no disposition line.
- **Where the falsification half attaches:** `tools/review-sweep.sh` already
  performs diff-form and digest comparison for clause 7's carry-forward
  (`sha256:` digests over a base..head range, reported on every terminal
  state). Property 4 is that same class of read, not a new mechanism.
- **The layer split is the story's spine and is NOT re-decided here.** Clause 11
  sorts the obligations by how each can be broken: an absence cannot be gated
  and is made visible; an act can be denied and belongs at a gate.
- `consulted: product-lab@4cc496b39be1d7641aaaaf678668fb64eda35f17 LESSONS.md:103`
  — *"A rule is enforced only at the layer where it can be broken … an
  obligation cannot be gated at all and needs its absence made visible … and
  when that layer belongs to another system, the carrier goes at the last
  boundary you control, with any gate upstream of it counting as ergonomics
  rather than control."* Clause 11 quotes it whole; kogaki#306's triage comment
  carries the reading.

## Acceptance criteria

**AC1 — a successor declares `supersedes: <blocked PR>`, and its absence is
REPORTED at `done`.**
Given a PR whose review record reaches the `done` boundary,
when it is a successor — it declares `supersedes:`, or the blocked PR it
continues was closed as superseded by it —
then a missing or unparseable `supersedes:` declaration is reported there.
**Reported, never gated**: the merge is governed by `blocking` alone
(kogaki#72), and clause 8 already holds that polarity for its own dispositions.

**AC2 — every finding open on the blocked PR carries a disposition on the
successor.**
Given the blocked PR's open findings at the moment it closed as superseded,
when the successor reaches `done`,
then each is listed with its `carried: #<N>` / `carried: register` /
`declined: <reason>` line, and each **undisposed** one is named. The grammar is
**clause 8's, lent** — a second vocabulary for "what happened to a finding"
would be a synonym in a join key, which is the defect clause 8 names by name.

**AC2a — a `carried:` naming an issue THIS MERGE CLOSES is not a disposition.**
Given a successor whose inherited finding carries `carried: #<N>`,
when `#<N>` is an issue the successor's own merge closes,
then it is reported as **undisposed**, not as satisfied. The disposition
evaporates at the moment a naive check reads it as present — present at the
`done` boundary, absent immediately after — so the carrier must **outlive the
merge**. **The natural check does not catch this**, which is why the criterion
is separate: kogaki#335's findings were `carried: #325` while #325 closed on the
successor's merge, and a new carrier had to be filed first. Assert the check
FIRES on that shape; a check that only reads for the line's presence satisfies
AC2 and fails this.

**AC3 — the base-postdates-the-corrective-merge property is checked, and the
check SAYS it is standing in for a gate.**
Given a successor PR,
when its base is resolved,
then the check reports whether that base contains the corrective merge — and
its output states plainly that **this is a check where clause 11 wants a gate**,
because the merge boundary is actor-level and outside this repository. A green
run that did not say so would read as the prohibition being in force, which is
the precise failure clause 11 records. This criterion is satisfied by the
disclosure as much as by the ancestry read.

**AC4 — an unchanged rebased diff falsifies the block's diagnosis and is
REPORTED — but ONLY where the block made a structural claim.**
Given a successor whose diff, taken against a base that postdates the corrective
merge, is unchanged from the blocked PR's,
when the block that produced it was justified by a **structural** claim,
then a finding is emitted saying that diagnosis is falsified. Never merged
quietly.

**AC4a — a PROCEDURAL block reports NO falsification.**
Given the same unchanged diff,
when the block was procedural — the bound was spent and the head moved — so no
diagnosis was made,
then **nothing is reported**. There is no claim for an unchanged diff to
falsify, and firing here is a spurious falsification. This is not hypothetical:
the rule's only real application, kogaki#335, is exactly this shape — a
procedural block whose rebased diff came out identical to `d36b15a` — so an
implementation built from AC4 alone reports a falsification of a diagnosis
nobody made. **Assert the NEGATIVE case**, and assert it against a procedural
block rather than an empty one.

**AC5 — every property has a fixture that FIRES.**
Given each of AC1–AC4a,
when the suite runs,
then each has a crafted case that **fails without the implementation**, per
`specs/SPEC.md` §4's fixture-discrimination bullet. A property whose check has
no firing case is how `catch_all_share` measured the wrong quantity through two
stories and a review round; a passing implementation with no discriminating
case does not satisfy this story.

**AC6 — each check enters with a BUDGET and a REMOVAL SIGNAL, not only a named
defect.**
Given `checks/registry.json`,
when the new checks are registered,
then each entry declares **four** things, not one: the **loop position** it runs
at, the **budget** it spends there, the **removal signal** that would justify
deleting it, and a **re-executable case** proving it refuses the defect it
names. `check-registry-conformance.sh` enforces the shape, so a wrong one fails
loudly — but the criterion is the four declarations, because the binding
quantity is total cost per ship-cycle and a suite that admits freely has no
shrink lever.

This story adds **up to six** members to a governed suite, which is why the
criterion is stated at admission economics rather than at schema conformance.
(Six *properties*; the four above are the *declarations* each admitted member
owes, and the two counts are deliberately different.)

> Kernel: a check suite is budgeted at its loop position; suite membership is
> opt-in per loop; admission carries a removal signal.

> Admission requires a REMOVAL SIGNAL DECLARED AT BIRTH, and retention runs on a
> catch ledger over EXERCISED runs; never-fired members are review candidates,
> never auto-deletions.

`consulted: product-lab@4cc496b39be1d7641aaaaf678668fb64eda35f17 topics/claude-code-ops.md:64`

**Consider how many members are owed at all.** AC1–AC4a are **six** properties
over **one** trigger (the supersession state), and the cheapest conformant shape
may be **one** registered member carrying six assertions rather than six members
each paying their own loop cost. Decide it and say which; a split that buys no
independent removal signal per member is the accretion this criterion exists to
price.

**AC7 — a NON-successor PR is untouched.**
Given an ordinary PR that declares no `supersedes:` and continues nothing,
when it reaches `done`,
then none of AC1–AC4a reports anything about it. The trigger is the supersession
state and nothing wider — clause 11 inherits clause 3's narrowness, and a check
that fired on every PR would be the accretion machine the check-suite economics
exist to prevent.

**AC8 — the stale division comment is repaired.**
Given `tools/review-sweep.sh:313` — *"kogaki#306 stays its own carrier: it owns
the REFUSAL surface"* —
when this story lands,
then it names the division that now holds: slot 1 folded into kogaki#305, the
rest carried by clause 11. Named as a criterion because a repair to a described
artifact that leaves its self-description standing is the class this repository
recorded on 2026-08-11, one file over.

## Story questions

- **SQ1 — how is "the blocked PR's open findings" READ at the successor's
  `done`?** The blocked PR is closed by then. Re-reading its review record is
  the obvious answer; whether the successor must instead *carry* the inherited
  list in its own body — so the check reads one artifact rather than two — is
  not settled by clause 11. Decide it in implementation and say which; a
  two-artifact read is correct only if the closed PR's record is reliably
  reachable.
- **SQ2 — what identifies "the corrective merge" mechanically?** AC3 needs a
  commit to test ancestry against. Clause 11 says "the fix that the block's
  diagnosis called for" and names no carrier for it. If nothing identifies it
  without a human reading, say so and report the property as
  cannot-determine rather than inventing a heuristic — a wrong ancestry verdict
  is worse than a stated absence.
- **SQ3 — does AC4's comparison need the blocked PR's diff after ITS base
  moved?** A blocked PR's own base may have advanced since it was blocked, so
  "unchanged" has more than one reading. Clause 7's existing digest machinery
  fixes one of them; state which you used and why the other is wrong here.

## Files this story is predicted to touch

`checks/check-review-report.sh`, `tools/review-sweep.sh`,
`checks/registry.json`.

`specs/SPEC.md` is **predicted NOT to change** — clause 11 was written by the
2026-08-11 triage sitting and this story implements it rather than amending it.
If implementation finds the clause underspecified, that is a stop-and-re-triage
condition (altitude: a story implements a decision, never makes one), not a
licence to edit the clause.

## Review Focus

- **AC3's disclosure is the criterion most likely to be dropped**, because the
  ancestry read is the interesting part and the sentence about standing in for
  a gate looks like commentary. It is the criterion.
- **AC7 is the narrowness guard.** Check that nothing here fires on an ordinary
  PR; clause 11's trigger is the supersession state.
- **AC2a and AC4a are the two criteria a natural implementation misses**, and
  both were found the same way — by re-reading kogaki#306's own comment, which
  recorded them at the rule's only real application. Both are stated as
  *negative* or *outliving* properties, which is exactly the shape a check
  written from the positive criterion passes without implementing. Verify each
  has a case that fires.
- **AC5 is where a lazy implementation shows.** Six properties, six firing
  cases — and mutation-testing each one is what this repository's own 2026-08-11
  sitting found to be the countermeasure that actually worked.
- **AC2 must LEND clause 8's grammar, never restate it.** A new token set here
  is a defect, not a convenience.
