`specs/SPEC.md` §4 clause 4 (the grant-derivation paragraph, kogaki#412) win.

## Story

As the review lane, I want a spawned round's executable grant computed over the
same tree the round will actually run in, so that a tool the PR under review
adds is runnable by the round reviewing it — which is what kogaki#412's AC1 has
asked for since it was filed, and what kogaki#413 merged without delivering.

## Context, and what is already settled

**The enumeration is not the defect and is not reopened.** kogaki#413 replaced
the check-registry-only grant with a filesystem derivation, which is the right
shape. The per-file form is *forced* rather than chosen: `Bash(bash checks/:*)`
is a measured dead grant (`tools/review-sweep.sh:175`, round 1's) and
`Bash(bash:*)` is a general shell refused by a shipped fixture
(`tools/review-sweep.sh:3740`). The open question is only *which tree the
derivation reads*.

**The two trees, read rather than inferred.** `TOOL_TOOLS` is built by
`os.listdir("tools")` in the shell prologue (`tools/review-sweep.sh:809-817`),
after the script's own `cd`, and frozen into `SWEEP_REVIEW_TOOLS`
(`tools/review-sweep.sh:868`) once per sweep. `spawn()` then creates a fresh
worktree at the PR's head sha via `make_worktree(tag, ref, detach)` and runs the
session with `cwd=tree`. Grant source tree ≠ round working directory.

**This story folds two of kogaki#412's four findings** — `input` and
`assertion` — because both edit `tools/review-sweep.sh` and the file-boundary
rule (`specs/spec-triage-gh/SPEC.md` §"Decomposition considers file
boundaries") prefers the overlap-minimising cut. The `scope` finding folds here
too for the same reason: the spawner exclusion lives in the same grant block.
The `control` finding is story 1.64 and touches `checks/` instead.
**Accepted overlap: none** — 1.63 and 1.64 share no file.

## Acceptance criteria

**AC1 — The grant is computed over the tree the round runs in.**
Given a sweep invoked from a checkout at `master`, and a PR whose head adds
`tools/<new>.sh`, when a round is spawned against that PR, then the session's
`--allowedTools` contains `Bash(bash tools/<new>.sh:*)`.
This is kogaki#412's AC1 verbatim and it is the acceptance item PR #413 left
false; a story that cannot demonstrate this has not discharged it.

**AC2 — The assertion is over the built grant string, never the source.**
Given the fixture set for this property, when a mutation emits
`Bash(tools/{n}:*)` — omitting the literal `bash ` — then at least one fixture
FAILS. An assertion that reads `tools/review-sweep.sh`'s own text rather than
the value handed to `--allowedTools` does not satisfy this criterion.

**AC3 — The live half declares its own vacuity.**
Given a tree whose derivation yields zero tools, when the fixture over the live
listing runs, then it reports itself vacuous rather than passing silently. An
empty derivation must not read as coverage — this is the defect PR #413's round
1 named and half-fixed.

**AC4 — The spawner is excluded by capability, not by filename.**
Given the grant derivation, when the exclusion is applied, then it is stated in
terms of the act that spawns rounds — clause 3's cap — and a fixture asserts
that a second spawner under a different filename is *also* excluded. The
current exclusion tests `n != "review-sweep.sh"`, which grants any renamed
spawner and says nothing about it.

**AC5 — `FIX_TOOLS` and `REVIEW_TOOLS` are decided in the same act.**
Given both roles, when the derivation changes, then both call sites are
covered, and a fixture asserts each role separately. PR #67's round 2 found a
grant fix that reached `REVIEW_TOOLS` and left `FIX_TOOLS` with the same dead
pattern — this criterion exists so that finding is not re-earned.

## Story questions — unverified, and deliberately not written as criteria

- **Where the derivation should sit inside `spawn()`.** `make_worktree()` is
  called *after* `cmd` is assembled, so either `cmd` moves below the worktree
  or the grant is recomputed and substituted. Both are reachable; which is
  cleaner is an implementation judgment this story does not pre-decide.
  *unverified — the ordering was read, the preferred repair was not.*
- **Whether the `fixture` grant class needs the same treatment.**
  `GRANT_CLASSES = ("reviewer", "fix", "fixture")` (`tools/review-sweep.sh:2292`)
  and this story covers the first two by AC5. Whether `fixture` spawns with a
  tool set at all is *cannot-determine — not consulted*, and is a question, not
  a criterion.
- **The `.sh` filter.** kogaki#412's reopen comment carries this as
  `carried: register` — the filter is the enumeration one axis over, with
  `.mjs` already shipping under `policy/kit/bin/`. Out of scope here by the
  issue's own declaration; named so it is not silently absorbed.
