## Story

As the owner reading an 11-group co-tag screen, I want to name the two or three
Groups and SubGroups I actually care about and get **one** Full Report of
exactly those — so that the reading is something I composed rather than eleven
files I have to triage.

## Grounding

- **Governing contract:** `specs/spec-terrain/SPEC.md` §11 v5 (the eager-vs-pull
  fork DISCHARGED to pull, unit = entered ID set), §12 v6 (generation trigger
  and the canonical `{ tag, ids }` identity), §6.3 v7 (the stop moves between
  the acts), all amended by the 2026-08-11 sitting that licensed this story.
- **The IDs already exist.** Story 1.56 (PR #354, merged 2026-08-11) minted
  `tokens.GroupID` `^G[0-9]+$` and `tokens.SubGroupID` `^G[0-9]+-[0-9]+$` in
  `specs/spec-terrain/report-format.json` v3, rendered on both covered
  surfaces. This story consumes them; it does not mint anything.
- **An inherited constraint, NOT re-decided here.** Story 1.56 AC11: G/SG ids
  are assigned in `COTAG_SORT` order and **a pin advance may renumber them** —
  an id is valid for the run that printed it. That decision was taken naming
  this issue. So an entered set is resolved against **the current screen's**
  composed groups, never against a remembered numbering.
- **What is being removed** (read, not inferred): `terrain/terrain.mjs:2111-2113`
  — `--all-groups`, `--group`, and the refusal that cites §11 v5's
  decided-eager contract in its own error text.
- **The identity today:** `reportIdentity` builds `query: { tag, group }`;
  `identityDigest` hashes `[pin, tag, group, judge]`.
- **The catch-all group name** is `NO_SECOND_TAG` = `(no second served tag)`;
  it is a Group like any other and gets a `G<n>` id, so it is enterable.
- `consulted: none — kogaki#314 is an owner decision recorded verbatim from the
  2026-08-09 hands-on session; the remedy-shape verdict on the issue carries
  the served line the classification leaned on.`

## Acceptance criteria

**AC1 — `report` takes an ID set and nothing else selects the material.**
Given `report --tag <T> --ids G10,G5-1,G5-2`,
when it runs,
then it writes ONE machine record and ONE owner rendering covering exactly
those three. `--all-groups` and `--group` are **gone**, not deprecated —
§11 v5 supersedes the eager path, and leaving the flag reachable leaves the
over-generation the decision removes.

**AC2 — the identity is `{ tag, ids }` with the ids CANONICAL.**
Given two runs entering the same ids in different orders,
when both complete,
then they share one identity and one artifact — idempotence is set-based
(§12 v6). The sorted list is what enters `reportIdentity` and
`identityDigest`.

**AC3 — the sort is NUMERIC-AWARE.**
Given ids `G10`, `G5-1`, `G5-2`,
when they are canonicalised,
then the order is `G5-1, G5-2, G10` — **not** the lexicographic `G10, G5-1,
G5-2`. Compare on the numeric components, never the raw string. This criterion
exists because the plain reading of "sorted" is wrong here and would render a
screen's tenth group above its fifth.

**AC4 — the rendering follows the canonical order.**
Given the report from AC2,
when it renders,
then its sections are in canonical order, and the entry order is neither
recorded nor honoured. §12 v6 states the cost: an owner cannot get a chosen
reading order by typing the ids in it.

**AC5 — an unresolvable ID refuses, naming the known set.**
Given `--ids G99`,
when `G99` is no Group or SubGroup of the current screen's composed groups,
then the run refuses and **lists the ids that do resolve**. A refusal that does
not say what was available sends the owner back to re-read a screen they
already read.

**AC6 — ids resolve against the CURRENT screen, never a remembered numbering.**
Given a survey record at a different pin from the one that printed the ids,
when the entered ids are resolved,
then they are resolved against the groups this run composes. Story 1.56 AC11
makes an id valid for the run that printed it, so nothing here may cache,
persist or reconstruct an earlier numbering.

**AC7 — a SubGroup id brings its SubGroup, not its parent.**
Given `--ids G5-1`,
when the report renders,
then it carries that SubGroup's members and claim — not the whole of `G5`. The
entered set is the unit; mixing `G5` and `G5-1` in one entry is admissible and
renders both, with `G5-1`'s members appearing under both, which is a cover and
not a duplication (§2.1).

**AC8 — §12's untouched properties stay untouched.**
Given a report spanning several groups,
when it is inspected,
then untruncated material, **pin-once**, rendering-not-an-address and the
repo-visible/uncommitted home (§12.2 v11) all still hold. #314 names these as
explicitly unaffected, and a multi-group report is where pin-once is easiest to
break.

**AC9 — §6.3's window still bounds what runs unattended.**
Given a co-tag screen,
when act 1 completes,
then nothing else runs until the owner speaks. Act 2 fires only on an entered
id set, and no prompt, selector or question mediates it (§6.3 v7).

## Story questions

- **SQ1 — what is the argument's surface form?** `--ids G10,G5-1` is assumed
  above for concreteness. Whether it is comma-separated, repeated (`--id G10
  --id G5-1`), or positional is not decided by #314 and does not change any
  criterion. Pick one and be consistent with the repo's existing flag style.
- **SQ2 — does the co-tag catch-all group need special handling?**
  `(no second served tag)` is a Group and gets a `G<n>`, so it is enterable by
  id like any other. No criterion treats it specially; flag it if the
  implementation finds a reason it must be.
- **SQ3 — what happens to a run that enters ZERO ids?** AC5 covers ids that do
  not resolve; an empty set is different. Refusing is the obvious answer and is
  not asserted here, because "the owner entered nothing" may be better read as
  "no report wanted" than as an error. Raise it rather than choosing silently.

## Files this story is predicted to touch

`terrain/terrain.mjs`, `checks/check-terrain-composition.sh`. The golden
specimens under `checks/fixtures/terrain/format/` are **predicted to change** —
the report's title line carries its group, and a multi-group report has no
single one — so AC2's identity change reaches the rendered bytes. The check
asserts byte-equality, so a wrong prediction in either direction fails loudly.

## Review Focus

- **AC3 is the criterion most likely to be got wrong**, because "sorted" reads
  as obvious and the obvious implementation is lexicographic, which is wrong.
- **AC1 is a removal.** Check no `--all-groups` survivor is reachable under
  another name.
- **AC6 forbids a cache.** The temptation is to persist the last screen's
  numbering so ids keep working; story 1.56 AC11 is why that is refused.
- **AC8 is where a multi-group report is most fragile** — pin-once was already
  repaired twice this week (kogaki#315, story 1.57), and spanning groups
  multiplies the surfaces that could reintroduce it.
