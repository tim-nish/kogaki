## Story

As the owner surveying Strands for an article, I want a settled Strand set's
**provenance neighborhood** enumerated and offered beside it, so that a
contemporaneous Grain under an unrelated tag is reachable rather than silently
excluded by the co-tag bound.

## Grounding

## Acceptance criteria

**AC1 — ONE input, the settled Strand set (§13.2 v15).** Given a settled Strand
set, when the subcommand runs, then it takes that set and nothing else. The
GroupClaim is a selection aid and is **not** an input. There is no Thesis
argument, and a run must not refuse for want of one.

**AC1a — the trigger is an explicit owner act (§13.2 v15).** Given a co-tag
screen, when the Strands and GroupClaim are settled and the owner has
explicitly named the set, then and only then may expansion fire. Firing earlier
fans out across a large number of Lessons; noise is a property of trigger
timing rather than of the substrate.

**AC2 — the three substrates enumerate (§13.3).** Given a settled set, when the
neighborhood is computed, then members are reached via `source_batch`
(same-sitting provenance), `cross_links`, and shared carrier issue, and each
member records **which substrate reached it**.

**AC3 — the join does not hold by equality (§13.3).** Given a Grain whose
`source_batch` is a legacy numbered value, when the batch-mate lookup runs,
then it joins through the batch record's `members` rather than by equality.

**AC4 — unresolved is marked, never empty (§13.3).** Given a `source_batch`
that cannot be resolved, when the lookup completes, then an **explicit
unresolved marker naming the value** is emitted, and an empty result is never
presented as "this Grain has no same-sitting siblings".

**AC5 — the bound is the DECLARED traversal and nothing else (§13.3 v16).**
Given the enumeration, when it is bounded, then it uses exactly the values §13.3
declares:

| substrate | depth |
|---|---|
| `source_batch` | one hop |
| `cross_links` | two hops |
| shared carrier issue | off |

**These are read from the spec, never chosen here.** An implementation that
picks different values has settled a spec question silently; one that derives
them from the settled set's content has reintroduced the input v15 withdrew.

**AC5a — the bound may change HOW MANY and never WHICH (§13.3).** Given two
runs differing only in the bound's values, when both complete, then the bound
may change *how many* neighbors surface and may **not** change *which*
enumerated neighbors surface by scoring, ranking or dropping them on relevance
— that is §13.5's extension, held behind its own trigger. An implementation
found scoring neighbors against any claim has both built the gated extension
and reintroduced the dead input.

**AC6 — empty is a result, in the form v16 leaves (§13.2).** Given an expansion
that reaches its stopping condition with nothing surfaced, when it completes,
then the outcome is reported as an informative empty rather than a failure.

**AC6a — the WEAKENING is honoured, not inherited silently.** The 2026-08-09
fill claimed to discharge AC6 "in the strong form" via a Thesis whose declared
substrates yield no members; that argument went with the Thesis. On v16's text,
empty is guaranteed informative only where the **enumeration itself** is empty.
Do not assert the strong form in output or in a check.

**AC7 — every property has a fixture that FIRES.** Given each of AC1–AC6a, when
the suite runs, then each has a case that fails without the implementation, per
§4's fixture-discrimination bullet.

**AC8 — the display-id slot is ANSWERED in this sitting, not stepped around.**
`deferred-slot: terrain-display-id-for-neighborhood-suggestions` (§14.6) — §13.7
states it **comes due here**, "in the sitting that implements §13, and before
code embeds an answer". §14.6 names three candidate shapes and decides none. A
suggestion is by construction **not in the survey record**, so §14.3's assignor
does not reach it and §14.3's no-element-names rule leaves the surface with no
token to render. **Raise it as a decision with alternatives and a receipt; do
not pick a shape in code.**

## Story questions

- **SQ1 — the bound's values are SETTLED; do not re-open them.** §13.3 v16
  declares them and kogaki#300 carries the selection with its alternatives and
  receipt. What is *not* settled is whether they are **right** — they are
  inherited from a fill that never ran. The named reopen trigger is a real run
  where a large settled set drowns the owner or a small one reaches nothing.
  **If this implementation's first real run shows either, say so; that is the
  measurement the spec asked for.**
- **SQ2 — what carries "the settled set" into the subcommand?** AC1a makes the
  trigger an explicit owner act, but the argument surface is not fixed by §13.
  Pick one consistent with the repo's flag style (story 1.58 chose `--ids` for
  the analogous case) and say which.
- **SQ3 — what does the neighborhood emit?** §13.1 makes it a report, never a
  proposal, upstream of selection with the full population reachable. Whether
  that is an artifact like `report`, or screen output like `cotags`, is not
  fixed here. Note §14.1's grammar covers `cotag_screen` and `full_report`
  only — a third surface is §14.1's own reopen trigger and is **not** this
  story's work.
