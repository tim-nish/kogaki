Umbrella: https://github.com/tim-nish/kogaki/issues/25. On conflict, the
umbrella issue and `specs/SPEC.md` §4 win.

As the Kogaki repository owner, I want every `consulted:` receipt to carry the
gateway's `request_id` and an outcome token, so that a consumer receipt and
the server's access-log row can be joined mechanically, and miss harvesting is
a grep rather than an interpretation.

## Context

`specs/SPEC.md` §4's sided-evidence clause is this story's governing text, as
amended for kogaki#25. The amendment is deliberately a **join key, not a
read**: the sidedness the clause establishes — the access log is the server's
record, `consulted:` lines are the consumer's — is preserved rather than
weakened, because carrying an id neither side dereferences into the other's
state is not a read of that state. Story 1.3's boundary
(`policy/consultation-map.md` entry 2) is untouched.

The receipt form ratified as D1 is
`Consulted: <question> @ <repo>@<sha> <file>:<line>`, which differs from what
this repo currently emits and parses. Story 1.8's receipts used the older
`consulted: <pin> <file:lines>` shape, and the shipped parser is:

- `checks/check-consult-receipts.sh:46` — `RECEIPT = re.compile(r'^\s*consulted:\s*(.+)$', re.MULTILINE)`
- `checks/check-consult-receipts.sh:47` — `PIN = re.compile(r'^(\S+)@([0-9a-f]{7,40})\s+(\S.*)$')`

`PIN` anchors the repo@sha at the **start** of the captured remainder, so a
receipt carrying a question before the pin fails `PIN.match` and is reported
as malformed. The grammar change therefore reaches the check, and the check's
malformed-receipt failure is the only thing it gates on
(`checks/check-consult-receipts.sh:13`).

The check's registry admission contract — "reports the branch's `consulted:`
receipt count and distinct pins, rendering zero explicitly … Fails only on a
malformed receipt, never on the count" (`checks/registry.json`,
`consult-receipts`) — stays **true** under the new grammar, so an admission
edit may not be needed. Its declared removal signal names a *gateway-side*
consumer receipt surface; a consumer-side join key moves toward that surface
without reaching it, so this story does **not** fire the removal signal.

An example receipt in the older form is rendered at
`.claude/skills/review-lane/SKILL.md:94` and needs the same carry-forward.

## Acceptance criteria

- **Given** a consultation through the seam, **when** its receipt is emitted,
  **then** the receipt carries the gateway's `request_id` for that response
  and an outcome token drawn from `hit` | `miss` |
  `uncovered-after-N-framings` (`specs/SPEC.md` §4, sided-evidence clause).
- **Given** a receipt carrying `request_id`, **when** the consumer side is
  read, **then** nothing dereferences that id into gateway state — the id is
  a join key held by whoever holds both sides, and Kogaki still reads only its
  own receipts (`specs/SPEC.md` §4; `policy/consultation-map.md` entry 2).
- **Given** a v2-form receipt, **when** `checks/check-consult-receipts.sh`
  parses it, **then** it is recognised rather than reported malformed — the
  `PIN` anchor at `checks/check-consult-receipts.sh:47` is the specific site
  that must accept the new shape.
- **Given** a v1-form receipt already in git history, **when** the check runs
  over a range containing it, **then** it is still recognised — the branch
  history is immutable, so a grammar change that invalidated past receipts
  would fail the suite on unrelated work.
- **Given** the check after this change, **when** its behavior is described,
  **then** it still **reports and never gates on the count**, failing only on
  a malformed receipt — this story changes what the parser accepts and
  nothing about what it enforces (`checks/check-consult-receipts.sh:2,13`).
- **Given** the receipt grammar, **when** it is documented, **then** it is
  documented in **both** `policy/kit/skills/consult-first.md` and
  `.claude/skills/consult-first/SKILL.md`, and the rendered example at
  `.claude/skills/review-lane/SKILL.md:94` is carried forward — a form
  declared in one copy makes conformance an enumeration of copies.

## Story questions (unverified — not acceptance criteria)

- Whether `request_id` is present on **every** gateway response shape, or
  only on the `policy_lookup` family, is **cannot-determine** from this repo:
  the field is served-surface behavior. Verify at implementation against the
  responses themselves rather than against `policy/CAPABILITIES.md`.
- Whether the registry admission text for `consult-receipts` needs an edit
  depends on the final grammar; it is predicted **not** to. If it does, that
  edit is the announced `checks/registry.json` overlap with story 1.11.
