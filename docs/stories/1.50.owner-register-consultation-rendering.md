Umbrella: https://github.com/tim-nish/kogaki/issues/320. On conflict, the
umbrella issue and `specs/spec-client-kit/SPEC.md` §8 win.

As the repository owner, I want a consultation to reach me as the question that
was asked, what the surface actually answered in readable words, and the
conclusion drawn from it, so that I can judge the reasoning instead of being told
only that a consultation happened — which is all a pin block says.

## Context

The contract was written in the same sitting that files this: §8 of
`specs/spec-client-kit/SPEC.md`, decided as alternative A of the coupled
#320 / #334 selection. **This story implements that section; it decides
nothing.** Where this body and §8 differ, §8 wins.

Four facts read before writing:

- **The kit has exactly one rendering of a consultation, and it is the audit
  artifact.** `policy/kit/bin/consult.mjs:402` composes `consult-receipt:` and
  `:507` re-reads it; `gateway-query.mjs` emits the `consulted:` block after the
  tool results. Nothing else exists, which is why a skill told to relay something
  better has had nothing better to relay — #320's own diagnosis.
- **The relay rule lives at `.claude/skills/consult-first/SKILL.md:79-113`** and
  currently points at the receipt.
- **`specs/SPEC.md:2549-2551` owns the receipt grammar** — `request_id`, outcome
  token, queries verbatim, and `disposition:` at a fork gate. §8 does not touch
  it, and neither does this story.
- **`lint-gate-declaration.py` is NOT in this repository** — it is installed
  actor-level at `~/.claude/hooks/` and owned by `claude-toolkit`;
  `.claude/hooks/` here holds only `review-trigger.py`. Read there at this pin, it
  requires `receipt:` **or** `outcome:` in a `recommendation` question, and
  `outcome:` alone satisfies it — so a gate can carry no pin and stay conformant
  (§8.4). **That is a source read, which is existence evidence**; whether its
  owner intends the form to remain admissible is a disposition only
  `claude-toolkit` can settle. No hook change is owed and none is proposed.

## Acceptance criteria

**1 — The kit emits the owner-register block.**
Given a consultation through `policy/kit/bin/consult.mjs`,
when it completes,
then it emits a block carrying the **Question** verbatim and the **Answer** as
the served line's readable text, in plain register, and that block contains no
`consulted:`, no `request_id:` and no `@<sha>`;
and the `consult-receipt:` block is still emitted, unchanged in grammar and
destination.

**2 — The emission is separable from the receipt.**
Given the two blocks,
when a caller wants one and not the other,
then each is independently selectable, so an owner surface can take the first
without the second and a PR body can take the second without the first.

**3 — The Conclusion is the agent's, and the rendering says so.**
Given the emitted block,
when it is rendered,
then it carries Question and Answer only, and the relay rule at
`.claude/skills/consult-first/SKILL.md` requires the agent to add exactly one
**Conclusion** line beneath it — because only the agent holds the conclusion.

**4 — The skill relays the emission and is never the sole carrier.**
Given `.claude/skills/consult-first/SKILL.md`,
when the relay rule is read,
then it points at the kit's emission rather than at the receipt,
and the kit's emission exists independently of the skill — `specs/spec-client-kit/SPEC.md`
§2 refuses skill-as-sole-carrier, and a test that passed with the skill alone
would not satisfy this criterion.

**5 — The pin-token deny ships as a declared FAST PATH, labelled as one, and it
is a REGISTERED check.**
It enters `checks/registry.json` with a complete admission record — the defect
class it carries, its licensing issue, its tier, its measured runtime, and a
**removal signal declared at birth** — because the served line binding entry 1 of
the consultation map requires exactly that, and because
`check-registry-conformance.sh` reaches an unregistered script nowhere, so an
unregistered fast path would ship with no removal signal and nothing would say
one was owed. **Decided here rather than left to the implementation**: leaving it
open would be the unnamed-deferral shape `specs/spec-client-kit/SPEC.md` §3.4 and
§7 q3/q4 spend this same decision refusing.

Given that registered check over owner-facing render helpers,
when it finds `consulted:`, `request_id:` or `@<sha>`,
then it reports;
and its own output states that it reaches **only the coined-identifier
sub-class** and that the positive admission test is `specs/spec-client-kit/SPEC.md`
§7 q4, named and unbuilt. A check presenting itself as complete coverage fails
this criterion — that presentation is the defect §8.3 exists to prevent.

**6 — A degraded consult emits no owner block either.**
Given an unreachable gateway,
when `consult.mjs` runs,
then it prints exactly one `policy_source unavailable:` line and exits 11,
and emits **neither** the receipt **nor** an owner-register block — a rendering
of an answer that was never served is the same fabrication the no-receipt-on-
degrade rule already forbids.

**7 — The install test covers the new emission.**
Given `policy/kit/test/install-test.sh`,
when it runs,
then it asserts the block's presence, its pin-freedom, its separability, the
degraded path, and that the relay rule points at the emission.

## Story questions (not criteria)

- **What a positive admission test at the owner-surface seam would be** — §7 q4.
