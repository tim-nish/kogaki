Umbrella: https://github.com/tim-nish/kogaki/issues/34. On conflict, the
umbrella issue and `specs/SPEC.md` §4 win.

As the Kogaki repository owner, I want the review lane's isolation recorded as
a requirement and its report's presence asserted at the merge layer, so that a
PR cannot reach merge on a review its own author performed — or on no review
at all.

## Context

`specs/SPEC.md` §4's PR-gate clause is this story's governing text, as amended
for kogaki#34. Two of the issue's four design items land here (1 and 4); the
transport for item 2 is story 1.13, and item 3's presence check is the
mechanical half specified below.

**The isolation clause has a specimen in this repository rather than an appeal
to principle.** PR #31 was reviewed from a non-authoring session and the review
caught a coined outcome-token set (kogaki#32) whose ratified form was sitting
unused in the authoring session's own context. That is the defect class an
author structurally cannot catch in their own work: not an oversight of fact,
but a failure to apply what was already held. The served ground is
`isolation-checks-are-control-arms` — some checks work precisely because they
know less.

**The split is the founding two-layer form, unchanged.** Whether a report
*exists*, authored outside the authoring session, is a computable fact and
belongs at the merge layer. Whether the report is *any good* is judgment and
stays in the lane. A check that read the findings would be the
judgment-in-the-mechanical-half defect the same clause refuses for the
boundary-receipt binding.

Existing carriers this story extends: `.claude/skills/review-lane/SKILL.md`
(the lane itself, which today has no isolation clause and no emission shape)
and `checks/registry.json` (six registered checks; registration requires a
full admission record including a removal signal declared at birth).

## Acceptance criteria

- **Given** a review-lane run, **when** it is performed, **then** the lane's
  own contract states that the reviewing session must not be the session that
  authored the work under review, and states why — a review by the authoring
  session cannot see what that session already held and failed to apply
  (`specs/SPEC.md` §4, PR-gate clause; `.claude/skills/review-lane/SKILL.md`).
- **Given** a review-lane report, **when** it is emitted, **then** it records
  enough for the presence check to find it and for a reader to tell which PR
  and which head commit it reviewed — a report that cannot be attributed to a
  revision is the staleness shape `proposals-carry-the-state-they-were-computed-against`
  governs.
- **Given** a PR, **when** the new registered check runs, **then** it asserts
  that a review-lane report **exists** for that PR and **never** reads the
  report's findings, verdicts, or severities (`specs/SPEC.md` §4).
- **Given** the new check file, **when** it is registered in
  `checks/registry.json`, **then** its admission record names the contract it
  uniquely carries, its licensing issue (kogaki#34), its tier and runtime, and
  a **removal signal declared at birth** — `check-registry-conformance.sh`
  fails an incomplete record, so this is enforced rather than remembered.
- **Given** fixtures under `checks/fixtures/`, **when** the suite runs, **then**
  both discriminating cases fire: a PR with a report (passes) and a PR without
  one (fails). A gate whose failing path is never exercised is the orphan-guard
  shape kogaki#6 exists to end.
- **Given** a review-lane finding that a consultation would have prevented,
  **when** the lane closes, **then** it emits a map-entry candidate in the
  kogaki#24 postmortem shape — the violating artifact, the trigger terms, and
  the question verbatim that would have found the served line — **as a
  proposal only** (`specs/SPEC.md` §4, consultation-map bullet).
- **Given** an emitted map-entry candidate, **when** it is handled, **then**
  admission remains a human act and the lane writes no entry itself: the
  proposal is mechanized, the admission is not (the founding two-layer split).

## Story questions (unverified — not acceptance criteria)

- **Where the report lives is undecided and is the load-bearing choice**: a PR
  comment, a commit-message trailer, or a file on the branch. It determines
  what the presence check can read — `check-consult-receipts.sh:38-44` reads
  commit messages plus `CONSULT_PR_BODY`, and inheriting that source set by
  proximity rather than by decision is how a scope gets set without anyone
  choosing it. Decide it explicitly at implementation.
- **How the check establishes that the report's author was not the work's
  author is unverified.** The isolation property is easy to state and may not
  be mechanically decidable from git and GitHub metadata alone. If it is not,
  say so: the check asserts presence, the isolation stays a stated obligation,
  and the gap is disclosed rather than papered over with a proxy that looks
  like enforcement.
