## Story

As the operator metering the two-round review cap,
I want a review round that was *spawned but whose outcome could not be read* to be
representable to the budget,
so that the cap counts rounds that were **paid for** rather than rounds that
happened to leave a readable artifact.

## Context — what the code actually does

Two instruments read the same artifact and disagree. On PR #174 round 2 the sweep
logged `report could not be verified (comment read failed) — not counted as
reviewed` while CI's `check-review-report.sh`, at the same head `ef586fd`, recorded
`ok: review-lane report present`.

**The merge gate was never compromised** and is out of scope: CI reads the PR
independently of the sweep's bookkeeping (`tools/review-sweep.sh` never
participates in it). A fix that touches the gate is fixing the wrong thing.

**The budget is derived, not incremented.** `rounds_used()`
(`tools/review-sweep.sh:1149-1158`) recomputes the count from the PR's own comment
bodies on every sweep — its docstring states *"This is the ONE place the count is
computed, and `decide()` calls it rather than re-deriving."* It is consumed by
`decide()` (`tools/review-sweep.sh:2023-2026`) against `MAX_ROUNDS = 2`
(`tools/review-sweep.sh:719`), and by the driver cap at
`tools/review-sweep.sh:2521-2522`. There is no persisted per-spawn ledger.

The three arms of the post-spawn dispatch:

- `tools/review-sweep.sh:2982` — `result != 0 or landed is False` → `spawn_failures`
  incremented, stall comment posted.
- `tools/review-sweep.sh:3002-3007` — `elif landed is None:` → prints and increments
  `counts['unverified']` **and nothing else**. No `spawn_failures`, no
  `post_stall_comment`, no `report_cost`.
- `tools/review-sweep.sh:3008` onward — `report-degraded`
  (`tools/review-sweep.sh:3019-3027`) or `report-landed`, both reached only when
  `landed is True`.

`landed` comes from `report_present()` (`tools/review-sweep.sh:1724-1747`), which
returns `None` on `CalledProcessError`/`JSONDecodeError`
(`tools/review-sweep.sh:1741-1742`, commented `cannot-determine, never "absent"`).

**Consequence, corrected from the issue's framing.** The issue says an unread report
"counts the round as spent". It does not: `counts['unverified']` is a display tally
printed at `tools/review-sweep.sh:3050` and never feeds the budget. The real defect
is the opposite and worse — the spawn is **free**, so an unbounded number of
`landed is None` sweeps can each spend a real review round against a two-round
budget that never moves. The degraded arm, by contrast, counts a round known to be
degraded. Both are records the guard cannot see through, because the guard reads
only `bodies` and neither state is representable there.

**Measured incidence:** one confirmed occurrence in `~/.kogaki/review-trigger.log`
(1801 lines at filing). The previously published figure of 47 was the union of two
unrelated patterns and is withdrawn on the issue. **Blast radius beyond this machine
is unknown and is stated as unknown** — the log is machine-local.

## Acceptance criteria

**AC1 — a cannot-determine round becomes representable.**
Given a spawned review session for PR *n* at head *h*,
when `report_present()` returns `None` (`tools/review-sweep.sh:1741-1742`),
then the sweep records the spawn somewhere `rounds_used()` can see, so that the
round is counted as spent rather than being free.

**AC2 — a cannot-determine is still distinguishable from a genuine absence.**
Given AC1's record exists,
when a later sweep reads it,
then the two facts remain distinct in the output: the existing honesty at
`tools/review-sweep.sh:3003-3004` ("Cannot-determine is not success") is preserved,
and the record does not assert that a report landed.

**AC3 — the unverified arm surfaces on the PR, as its siblings do.**
Given the `landed is None` arm at `tools/review-sweep.sh:3002-3007`,
when it fires,
then a stall comment is posted in the same manner as the `spawn-failed` arm
(`tools/review-sweep.sh:2990`) and the `report-degraded` arm
(`tools/review-sweep.sh:3023`), so the fact does not survive only in that run's
stdout.

**AC4 — the merge gate is untouched.**
Given this story's diff,
when it is reviewed,
then `checks/check-review-report.sh` and CI's report-reading path are unmodified,
and no acceptance criterion above depends on them.

**AC5 — WITHDRAWN 2026-08-07; the criterion moved to story 1.38 (kogaki#204).**
It read: *"a poll never re-fires the trigger it waits on — given
`tools/review-sweep.sh --spawn --pr <n>` invoked repeatedly while waiting, when
the same PR is already in a spawned round, then a second session is not spawned
for that round."*

**Withdrawn rather than deleted**, so a reader holding the prior version finds
the disposition rather than an absence. The criterion is **not dropped**: it is
now story 1.38's whole subject, licensed by kogaki#204 and governed by
`specs/SPEC.md` §4 clause 4.

The bundling was the defect kogaki#204 was filed to fix — its body says so:
*"this issue exists so it keeps a carrier once AC5 comes out of that story."*
Until this edit the coming-out had not happened, so **two published stories
licensed the same implementation** and nothing observed the double-build. The
guard itself was never in dispute; only its home was.

This story's own scope is unchanged and is the issue's **first** cause: making a
`landed is None` round representable to `rounds_used()`. That is a **reader**
defect. AC5's is a **writer** defect — the spawn path does not know a round is
in flight — and no repair to what `rounds_used()` can see gives it one.

**AC6 — the fixtures cover this story's arm.**
Given the file's self-test blocks (`tools/review-sweep.sh:2510-2530` exercises
`drives_fix`/`rounds_used`),
when this story lands,
then cases exist for the `landed is None` path. The re-fire guard's fixture
rides story 1.38 with the guard itself, per the withdrawal above.

## Story questions — carried as questions, never as criteria

- **Where should the spawn record live?** The tool has no persistent per-round state
  today; the only JSON state file (`_state = _gate_file + ".json"`,
  `tools/review-sweep.sh:2420`) belongs to the denial-gate fixture, not to rounds.
  Whether AC1's record is a PR comment (visible to `rounds_used()` for free, and the
  cheapest option) or new machine-local state (which `rounds_used()` cannot currently
  read) is **undecided** and is a design choice for the implementing sitting.
  *Unverified inference:* a PR comment appears cheapest because `rounds_used()`
  already reads comment bodies — but whether a cannot-determine marker should be
  `performed()` (`tools/review-sweep.sh:1158`) is exactly the AC2 question and is not
  settled here.
- **Is the true incidence higher than one?** Cannot-determine — the log is
  machine-local and covers only this machine's history. No criterion asserts a rate.

## Out of scope

- The two-round cap itself (`MAX_ROUNDS = 2`, `tools/review-sweep.sh:719`).
- CI's `check-review-report.sh` and the merge gate (AC4).
- The `report-degraded` arm's semantics (`tools/review-sweep.sh:3019-3027`) — it is
  a quality flag on a round that *was* counted, not a read failure, and conflating
  the two produced the withdrawn figure of 47.
- Whether the review lane's widening trigger has fired at three-of-a-class. That is
  the register reader's call, and the register's own carrier is under repair at
  kogaki#191.
