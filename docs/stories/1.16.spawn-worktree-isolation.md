Issue: https://github.com/tim-nish/kogaki/issues/61. On conflict, the issue
and `specs/SPEC.md` §4 win.

As the Kogaki repository owner, I want every spawned session to run in its own
worktree outside the repository, so that concurrent sessions cannot move HEAD
under one another and the rally driver's routine spawning stops being a race
the owner has to survive.

## Context

`specs/SPEC.md:152` is the governing text and it is already written: spawn
orchestration lives in the lane-command layer. This story applies an
**already-ratified** invariant to that layer rather than proposing a new one —
`/ship-cycle`'s execution-isolation rule: *one isolated worktree per item in
flight, created outside the repository, or sequential; there is no third mode.*

**The specimen is an incident, not a hypothesis (owner-reported, 2026-08-05).**
Two live sessions shared one working tree; one moved HEAD under the other
mid-commit; a kogaki#52 commit landed on the kogaki#56 branch and was pushed
there. It was recovered without data loss — explicit-path staging kept the
commit clean, and an owner-approved repoint, rebase and force-push left PR #57
carrying only its own change. Survivable is not impossible, and PR #59 has now
made shared-tree spawning **routine**: `tools/review-sweep.sh:464` spawns a
fixer that edits and pushes, and `tools/review-sweep.sh:253` spawns a reviewer
that runs `bash checks/*.sh`, both concurrent with the authoring session whose
push fired the hook.

`tools/review-sweep.sh:275` is the site, and the defect is an **absence**:
`subprocess.run(cmd, stdout=log, stderr=subprocess.STDOUT, check=False)` passes
no `cwd`, so every spawned session inherits whatever tree the sweep happens to
run in. A repository-wide grep for `cwd` in that file returns nothing.

**The isolation belongs in the spawn helper, not at its call sites.** Both
sessions reach the process through one `spawn()`
(`tools/review-sweep.sh:253`), so siting the worktree there covers spawn kind
N+1 by construction. A per-call-site rule would be the enumeration-coverage
shape one level down, which the served surface rules against:

> Per-repo installation is the prohibition-accretion shape in mechanical form:
> it makes coverage an ENUMERATION OF REPOS, so repo N+1 is uncovered by
> default and each new consumer silently re-opens the hole.

`consulted: product-lab@ed47fbd3818b9a66954a558d6c88e86574407ece topics/claude-code-ops.md:54`

## Acceptance criteria

1. **Given** a session is about to be spawned, **when** `spawn()` runs,
   **then** it creates a fresh `git worktree` **outside** the repository
   directory and points that session's working directory at it. Outside is
   load-bearing: a worktree under the repo root is still inside the tree the
   authoring session's own tooling walks.

2. **Given** a session has exited, **when** `spawn()` returns, **then** the
   worktree is removed — on **every** exit path, including a non-zero exit and
   an exception, not only on success.

3. **Given** removal fails, **when** that failure is observed, **then** it is
   **reported, never swallowed**. A silently leaked worktree is the failure
   mode this criterion exists to refuse; the sweep already applies the same
   discipline to a failed spawn (`tools/review-sweep.sh:465-470`), which it
   reports and reflects in the exit code rather than printing success over.

4. **Given** a worktree was created, **when** the route log is written, **then**
   its path rides that log — beside the command line `spawn()` already writes
   first (`tools/review-sweep.sh:272-274`) — so a leaked worktree is findable
   from the record rather than by searching the filesystem.

5. **Given** the fixer session commits and pushes, **when** it runs in its own
   worktree, **then** it does so from a clean tree regardless of what the
   human's tree holds mid-edit. This is the second property the isolation buys
   and it is stated as a criterion so it is not lost as a side effect.

6. **Given** the sweep runs in `--dry-run` mode, **when** it previews a spawn,
   **then** it names the worktree it would create, on the same ground the
   preview already names the model and the cap
   (`tools/review-sweep.sh:478-481`).

## Story questions

- **Which ref does the worktree check out?** The reviewer reads a PR's head;
  the fixer must commit onto that PR's branch and push it. A detached worktree
  at the head sha would serve the reviewer and break the fixer's push.
  **Unverified — the branch each spawn needs is not recorded in
  `tools/review-sweep.sh` today**, which reads `head` as a sha
  (`tools/review-sweep.sh:436`). Resolving head-sha to head-ref is likely one
  more field on the `gh pr list` read the sweep already makes; confirm before
  implementing rather than adding a second API call.

- **Where is "outside the repository"?** A sibling directory, a path under the
  system temp root, or an operator-declared home are all admissible and the
  invariant does not discriminate. **Cannot-determine — no served position was
  consulted on the location**, only on the isolation itself. Pick one and
  declare it in the route log per criterion 4; if it becomes a capability the
  repo needs but cannot install, it registers into `deps/registry.json` (story
  1.14).

## File boundaries

Touches `tools/review-sweep.sh` only. **Accepted overlap:** story 1.15 edits
the same spawn path. Sequenced against it, never a `depends_on` — the two
changes are independent behaviors on one helper, and the overlap is a
scheduling edge.
