Umbrella: https://github.com/tim-nish/kogaki/issues/100. On conflict, the
umbrella issue and `specs/SPEC.md` §4 (the third review-conduct clause) win.

As the owner of the review pipeline, I want a spawned reviewer that meets a
refused command to record it and move on, so that one missing grant costs one
capability instead of the entire review.

## Context

`specs/SPEC.md` §4's third conduct clause (added under kogaki#100
alternative A) is this story's governing text. The rule already shipped as
prose in kogaki#74's `COMPOSITION` prompt — `tools/review-sweep.sh:759`
("never re-attempt a refused command in another form") and `:775` ("Do not
spend turns probing for a form that gets through") — and was measured failing
on the next PR: on PR #98 the post-kogaki#74 prompt was present in the second
spawn's own context while that spawn spent its last four turns rephrasing one
refused command.

The served position gives both the diagnosis and the siting: a prohibition
needs a mechanical gate at the tool boundary, and where that boundary belongs
to another system the carrier goes at the last boundary you control
(`consulted: product-lab@f918c5158c718394b3a0e4f10239d75bbb451b74 LESSONS.md:87`).
The permission boundary is the harness's, so the carrier is the spawn wrapper.

**THE BLOCKING SLOT IS FILLED — AC 3 IS UNBLOCKED** (owner decision
2026-08-06, recorded on kogaki#100; `specs/SPEC.md` §4, the
`refusal-signal-source` fill). AC 3 was held because
`deferred-slot: refusal-signal-source` had not been decided. It now is:
**the EVENT is primary and the TERMINAL FIELD is the backstop.** Prevention
keys on the in-session `{"type":"system","subtype":"permission_denied"}` stream
event; the terminal `permission_denials` field of the `{"type":"result"}`
record stays as the guaranteed measurement path. The declined alternatives —
the terminal field alone, the event alone, and keying on `is_error: true` —
their reasons, the measurement the decision was made on, and the two premises
the clause states are recorded in the spec and on kogaki#100.

What the fill supplies to this story, and what it adds to it:

- **The fork as this story stated it was mis-framed, and that is now known.**
  There is no "in-session `permission_denials` field": the key appears on
  **zero** non-`result` objects across every route log in `~/.kogaki/reviews/`.
  The in-session signal is a differently-named **event**, 1:1 with the terminal
  field by `tool_use_id` **within every log that carries events**, arriving with
  real lead time (PR #102: line 33 of 189). **The share, so "1:1" is not read as
  "everywhere":** the unit is events — 40 at the close-of-run count, against 294
  denials in the corpus — because only the 7 logs from the 2.1.223 boundary
  onward carry the event path at all. That is the version premise seen from the
  other side, and it is why AC 6 exists.
- **The event is CLI-version-scoped, and the clause states that as a premise
  rather than assuming it.** The carrier **degrades to the terminal backstop,
  never to nothing** — new **AC 6** below makes the absence observable, because
  an absent event generates nothing to gate.
- **The failed/refused counter is discharged; the rephrase-able one is not.**
  Keying on the event (never on `is_error`) cannot read a transient failure as
  terminal — measured: none of the ordinary failures carries a denial event or
  field. But the log **does not distinguish a rephrase-able denial from a
  dead-end one**, so AC 3 is restated to say what "terminal" does and does not
  claim.
- **One shape fact:** the event carries `tool_name`, `tool_use_id`, `message`
  and `decision_reason_type` — **not `tool_input`**. A live reader wanting the
  `Bash(<first three words>)` label `denied_tools()` renders must **join
  backwards** to the preceding `assistant` tool_use block by `tool_use_id`.
- **Unproven, and not to be implemented as though it were:** every observed
  event was `tool_name: "Bash"`. MCP-tool, `Write` and `Edit` denials are
  **unproven on the event path** and reach only the terminal field.

ACs 1, 2, 4 and 5 were implementable without the fill and are unchanged.

## Acceptance criteria

1. **Given** the report grammar, **when** this ships, **then** it carries a
   `cannot-determine: <dimension> — <why>` line, so a reviewer blocked by a
   refused capability has somewhere to put the blocked dimension instead of
   retrying. The grammar lives beside `review-scope:` and `report-complete:`
   and is documented in the same header block
   (`checks/check-review-report.sh:49-55`).

2. **Given** a report carrying `cannot-determine:` lines, **when** the
   mechanical half runs, **then** those lines are **reported and never gated**
   — they are not findings, they do not affect `report-complete:` count
   equality, and they never block. Whether a blocked dimension should have been
   obtained is the lane's judgment, which is where `specs/SPEC.md` §4 already
   puts scope honesty (clause 5, `specs/SPEC.md:130`), and this criterion
   places the new line on the same side of the split.

3. **UNBLOCKED — the slot is filled (event primary, terminal backstop).**
   **Given** a spawned reviewer whose command is refused, **when** the wrapper
   observes the in-session
   `{"type":"system","subtype":"permission_denied"}` stream event, **then** that
   command is terminal: a second attempt in any rephrasing is itself refused,
   and the session is routed to AC 1's `cannot-determine`. The key is the
   **event**, never `is_error: true` — that is what makes the carrier unable to
   read a transient failure as terminal, and it is the measured ground on which
   the slot's own counter-argument is discharged.

   Two things this criterion does **not** claim, stated so the implementation
   does not quietly claim them:

   - **"Terminal" is about the command, not about the intent.** The log does
     not distinguish a rephrase-able denial from a dead-end one:
     `decision_reason_type: subcommandResults` names one offending sub-part of a
     compound command — the class kogaki#74 found had granted alternatives —
     and the field is absent on roughly a fifth of events, so it is a weak hint
     and never a discriminator. Naming a granted alternative stays the
     `COMPOSITION` prompt's static job (AC 4); the signal cannot compute it.
   - **Event coverage is proven for `Bash` only.** MCP-tool, `Write` and `Edit`
     denials are unproven on this path and reach only the terminal field, so a
     non-Bash denial is expected to fall through to AC 6's reconciliation rather
     than to be prevented.

   The label the terminal set is keyed on is not free: the event carries no
   `tool_input`, so the command text must be **joined backwards** from the
   preceding `assistant` tool_use block by `tool_use_id`. Whether the key is the
   raw command string or a normalized form is this story's to settle and is not
   a named slot.

4. **Given** the `COMPOSITION` prompt at `tools/review-sweep.sh:755-776`,
   **when** this ships, **then** the prompt text is **kept** and reclassified in
   its own comment as **ergonomics rather than control** — the served line's own
   word for a gate upstream of the violation layer. Deleting it would remove a
   useful hint; leaving it unmarked would let the next reader take it for the
   carrier again.

5. **Given** the spawn's result record, **when** a review ends, **then** the
   count of refused-and-terminated commands is recorded in the run log
   alongside the existing per-round route data
   (`~/.kogaki/reviews/pr-<n>-round-<r>.log`, the file whose
   `permission_denials` field supplied this issue's measurements). This is the
   rate signal that says whether the grant table is the real problem; without
   it the remedy hides its own evidence. **The count comes from the terminal
   field**, which is present on every spawn at every CLI version observed, so
   the measurement half never degrades with the event.

6. **NEW, and it is the fill's own carrier.** **Given** a spawn that has ended,
   **when** the run-log record is written, **then** the wrapper **reconciles the
   two signals and states the result**: the number of `permission_denied` events
   it observed in-session against the number of entries in the terminal
   `permission_denials` field. An event path that is absent — an older CLI, or a
   denial class the event does not cover — must then read as *"prevention
   unavailable this run — N denials measured, 0 prevented"* and **never as
   "no denials"**.

   This exists because the prevention half rests on a **stated premise** (the
   harness emits the event; observed present on CLI 2.1.223, observed absent on
   2.1.222) and an absent event generates nothing to gate. `specs/SPEC.md` §4's
   fill states the premise and names the scope; this AC is the visible-absence
   signal that keeps the premise honest, per the served rule that an obligation
   cannot be gated and needs its absence made visible
   (`consulted: product-lab@f918c5158c718394b3a0e4f10239d75bbb451b74 LESSONS.md:87`,
   `topics/archive/knowledge-architecture.md:177`). It is a **report, never a
   gate**: no version preflight, and the lane is never withheld for a missing
   event. It is also the mechanism that would observe the unproven part — a
   terminal denial with no matching event is what a non-Bash denial looks like.

## Story questions

- *Is a `cannot-determine` line owed a count token of its own?* `report-complete:`
  counts findings and AC 2 excludes these lines from it. Whether completeness
  should also assert how many dimensions were abandoned is not decided here.
- *Does AC 5's count belong in the run log only, or also in the report?* The run
  log is machine-local; the report is the durable surface. Which carrier the
  rate signal needs is **unverified — no served position consulted on it this
  sitting**, so it is a question rather than a criterion.
