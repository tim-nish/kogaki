As a stacked PR whose elder has squash-merged, I want the review report I
already earned to survive a rebase that provably changed nothing, so that the
pipeline's own mandated step stops producing parks with no legal exit.

## Context

Four clauses, each correct alone, compose into an unmergeable state: the
toolkit mandates a post-squash rebase
(`~/work/claude-toolkit/commands/implement-story.md:250`, restated at `:418`);
a rebase necessarily produces a new head; the head sha is part of presence
(`checks/check-review-report.sh:44`); and `specs/SPEC.md:125` bounds the rally
at two rounds, "never a third". Observed on PR #89 — cleared only by an owner
`--admin` merge bypassing branch protection, over a rebase whose pre- and
post-rebase diffs were byte-identical.

`specs/SPEC.md` §4 clause 7 (added under kogaki#96 alternative A) is this
story's governing text. It admits a **second instrument for the same pin**:
content-equality alongside sha-identity, recomputed and recorded as a gate
event.

**THE BLOCK IS LIFTED — `report-base-resolution` IS FILLED.** `specs/SPEC.md`
§4 clause 7 carried `deferred-slot: report-base-resolution` — how the check
obtains the base of head A. The owner filled it on 2026-08-06 at a decision gate
on kogaki#96, selecting **(c): the base is RECORDED IN THE REPORT**, with (a)
the PR's current base and (b) the merge-base at A both declined and their
reasons recorded in the clause. This story is no longer held: every AC below is
dispatchable.

What the fill supplies to this story, and what it adds to it:

- **The base of head A is a READ**, taken from the report's own `review-base:`
  line, rather than a derivation. AC 1 says so directly now.
- **The report grammar gains one adjacent line** — `review-base: <base sha>`,
  beside `review-scope:` and `report-complete:`, over the same segmenter, first
  declaration wins. The report token is **never widened**; that form was
  exercised and failed in story 1.17. New **AC 7**.
- **Pre-field reports carry no base**, and fall back to **(b), the merge-base
  at A** — never (a). The fallback is transitional and expires with the last
  base-less live report. New **AC 8**.

## Acceptance criteria

1. **Given** a PR whose head is B and whose only report names head A, **when**
   the check runs, **then** it computes the PR's diff against its base at B and
   the diff the report reviewed at A — **resolving A's base by READING the
   report's own `review-base:` line**, per `specs/SPEC.md` §4 clause 7's filled
   `report-base-resolution` (c) — and if the two are byte-identical the report
   is `present` for B rather than `stale`. `stale` is today's outcome and is
   produced at `checks/check-review-report.sh:392` (`return 'stale', shas`),
   which is the branch this criterion changes. The base is **read, never
   derived**, whenever the line is present; the one case where it is derived is
   AC 8's transitional fallback.

2. **Given** a carry-forward occurs, **when** the check emits its result,
   **then** the output NAMES both diffs it compared and the comparison's
   outcome, so a later reader can re-run it. A carry-forward that leaves no
   record is the silent re-derivation `specs/SPEC.md` §4 clause 7 forbids,
   quoting `product-lab@f918c515 topics/articles.md:73` at its pin.

3. **Given** either diff cannot be computed — an unresolvable base, an
   unreadable revision — **when** the check runs, **then** the result is the
   existing `stale` state and NEVER a carry-forward. Failing toward the
   reviewed side is the same choice `head-unknown` already makes at
   `checks/check-review-report.sh:389`, whose comment at `:386-388` records the
   ground: "making it optional exactly when it cannot be checked, with the
   permissive value as the fallback, is failing open".

4. **Given** a rebase that changed content, **when** the check runs, **then**
   no carry-forward occurs — the diffs differ and the report is `stale`, as
   today.

5. **Given** the round counter, **when** a carry-forward occurs, **then** the
   round count is unchanged: a carry-forward is not a round and consumes none.
   The round bound at `specs/SPEC.md:125` is untouched by this story.

6. **Given** the check's own inline fixture suite, **when** this ships,
   **then** it covers at minimum the cases below. The suite is the existing
   one — `FIXTURES` at `checks/check-review-report.sh:428` driven at `:481`,
   and `DECL` at `:504` driven at `:563`; this extends it rather than adding a
   second harness.

   - **identical-diff carry-forward** — same recorded base, byte-identical
     diffs, report `present` for B.
   - **changed-diff no-carry-forward** — same recorded base, diffs differ,
     `stale`.
   - **moved-base no-carry-forward** — the report's `review-base:` names a base
     that is **not** the PR's current base, **and the move changes the diff**;
     result `stale`. See the note below: this case is stated more precisely
     than it was, because as originally written it was not decidable.
   - **moved-base-but-identical-diff CARRY-FORWARD** — the base moved and the
     diff is nonetheless byte-identical; result `present`. This is the
     companion the previous case needs in order to be testing anything: it is
     the case that distinguishes "the base moved" from "the reviewed content
     changed", and §4 clause 7's subject/instrument rule makes the
     carry-forward correct here.
   - **uncomputable-diff staleness** — either diff unreadable; `stale`, never a
     carry-forward.
   - **base-less report** — no `review-base:` line, exercising AC 8's
     transitional fallback rather than being treated as a missing base.

   **AC 6 was repaired here rather than carried over, and this is why.** As
   originally written it read "moved-base no-carry-forward" with no further
   qualification, and a round-2 review found that under resolution **(a)** —
   the PR's current base — the fixture **inverts**: (a) takes *both* diffs
   against the same current base, so a base move produces no difference at all,
   the diffs compare equal, and the carry-forward fires. The expected outcome
   the AC names is unreachable under (a); the fixture would have had to be
   written with the opposite expectation or not at all. Under the selected
   **(c)** the case is reachable — the recorded base for A and the current base
   for B genuinely differ, which is exactly the visibility (c) buys — so the AC
   is **correct in direction under (c)**.

   It was still **not correct as stated**, and the review's finding is what
   exposed it. A moved base does not *entail* a different diff: a base that
   moved over unrelated files leaves the diff byte-identical, and under (c)
   that case carries forward. So "moved-base no-carry-forward" as an
   unqualified rule is false under (c) too — it is true only when the move
   changed the diff. Both halves are now named as separate fixtures, because a
   suite carrying only the refusal half would encode the false rule and pass.
   The same imprecision is repaired one line up in `specs/SPEC.md` §4 clause 7's
   weakening paragraph, which previously read that a moved base "yields a
   different diff and no carry-forward".

7. **Given** the report grammar, **when** this ships, **then** a report may
   declare `review-base: <base sha>` on **its own adjacent line** beside
   `review-scope:` and `report-complete:`, and the check reads it in the **same
   single pass** over the **same segmenter**: anchored whole, 7–40 hex
   characters exactly as the report token accepts, **first declaration wins**,
   a second being a malformed report rather than a correction. **The
   `review-lane report:` token is NOT widened** — that form was exercised and
   failed in story 1.17, and its regex lives in two files
   (`checks/check-review-report.sh:188`, `tools/review-sweep.sh:628`), both of
   which an adjacent line leaves untouched. A `review-base:` appearing in a
   finding's prose is a **mention**, never a declaration, on the same whole-line
   anchoring clauses 5 and 6 already use.

8. **Given** a report carrying **no** `review-base:` line — every report
   written before this ships — **when** a carry-forward is evaluated, **then**
   A's base is derived as the **merge-base at A** (resolution (b)), and **never**
   as the PR's current base (resolution (a)). Where that derived base is not the
   base actually reviewed, the diffs differ and the result is `stale`, which is
   AC 3's fail-toward-the-reviewed-side behaviour and the safe outcome. The
   fallback is **transitional**: it is keyed on the line's absence alone, takes
   no flag and no configuration, and expires when the last base-less report is
   no longer live on an open PR. It is not a second permanent base resolution.

## Blast radius

- `checks/check-review-report.sh` — the `find_report` state machine, the
  `review-base:` reader (AC 7), and the inline fixtures. **Accepted overlap
  with story 1.28**, which adds a `cannot-determine` line to the same file's
  report grammar; 1.28 declares `depends_on: 1.26` so the two land in sequence
  rather than concurrently. Filling the slot to (c) **enlarges** that overlap
  as the story question below predicted: both stories now add an adjacent
  declaration line to one grammar, over one segmenter. The sequence bound is
  what keeps that safe and is unchanged.
- `specs/SPEC.md` — amended twice: by the sitting that created this story, and
  by the sitting that filled `report-base-resolution`. **No further spec edit
  is owed here.**
- `.claude/skills/review-lane/SKILL.md` — **now in radius.** §"The report's
  shape" is the reviewer-facing grammar and must gain `review-base:` with its
  read-the-sha-as-a-value rule (kogaki#91), or the reader ships with nothing
  emitting the field it reads.
- `tools/review-sweep.sh` — **NOW IN RADIUS, and this is a change from the
  original story, which declared it unchanged.** Round counting still is not
  touched; what is, is the **reviewer prompt** at `:726`, which enumerates the
  adjacent declaration lines a report may carry and today does not mention a
  base. A reader-only implementation would gate on a field no emitter writes,
  so every report would take AC 8's transitional path forever and (c) would
  ship in name only. **Serialization note:** story 1.27 also edits
  `tools/review-sweep.sh`. These two must not land concurrently — sequence
  them, as 1.26/1.28 already are.
