umbrella issue and `.claude/skills/review-lane/SKILL.md` win.

As the Kogaki repository owner, I want the reviewer to read CI output it has
already paid for and to read tool output through bounded commands, so that a
review spends its turns on judgment rather than on re-deriving facts that exist.

## Context

kogaki#70's sinks 2 and 3, both measured from PR #67's route logs rather than
estimated. Round 1 ran `check-consult-receipts.sh` twice; round 2 ran the
**entire suite in a for-loop** plus individual checks — while the same suite had
already run in CI against the same head. Separately, round 2 spent ~8 turns
probing its own sandbox and read a 70 KB transcript in three `cut -c` byte
slices.

**The permission already exists and is the wrong strength.**
`.claude/skills/review-lane/SKILL.md:73` says "Run that check (**or read its CI
output**) and quote its lines" — a free choice where the costs differ by two
orders of magnitude. This story makes the cheap branch mandatory *when a
completed CI run exists for the head*, which is a tightening of an existing
permission rather than a new obligation.

**Why the bound on tool reading is not style advice.** A reviewer that needs a
parser is describing a gap in the sweep's own instruments — kogaki#65 item 3
gave the sweep a denial extractor for exactly this reason. Improvised byte
arithmetic inside a per-PR review re-derives, per round, something that belongs
once in the tool.

## Acceptance criteria

1. **Given** a completed CI run exists for the PR's current head, **when** the
   reviewer needs a registered check's result, **then** it reads that run's
   output (`gh pr checks` plus the run log) and does not re-run the check
   locally. `Bash(gh run:*)` is already granted (kogaki#65).

2. **Given** CI has **not** completed for the current head, **when** the
   reviewer needs a check's result, **then** running it locally is permitted —
   and waiting for CI is preferred over duplicating it where the wait is
   bounded.

3. **Given** the reviewer reads any tool output, **when** it does so, **then**
   it uses bounded, purpose-shaped commands. Ad-hoc byte slicing of a large
   transcript is out of scope for a per-PR review; a reviewer that needs a
   parser **files for one on kogaki#13** rather than improvising it inline.

4. **Given** a probe about the lane's own sandbox or grants, **when** the
   reviewer is tempted to run it, **then** it is recognised as **register
   work, not per-review work** — recorded once on kogaki#13, never re-probed
   each round. The kogaki#65 grant-escape finding is the specimen: genuinely
   valuable, and paid for on every round it is rediscovered.

5. **Given** these bounds, **when** a check's result cannot be obtained from
   either source, **then** the report says **cannot-determine** and names which
   source failed — silence is never a pass, and the existing dimension-2
   discipline is unchanged.

## Story questions

- **What is "a completed CI run" when the suite is partially red?** PR #67's
  own reviews hit this: the mechanical half was red for the presence gate while
  every other member passed, and the reviewer could not tell one from the other
  without the job log. **Unverified — whether `gh pr checks` alone
  discriminates per-member results was not tested this sitting.** If it does
  not, criterion 1 needs the run-log read rather than the summary.
  **Closing act, named (PR #71 review): this is answerable from THIS PR's own
  CI run** — the suite ran registry-driven with one member red and the rest
  green, which is exactly the partially-red case. The implementer reads that
  run with `gh pr checks` and then with `gh run view --log`, and compares what
  each discriminates. No new experiment is owed.
