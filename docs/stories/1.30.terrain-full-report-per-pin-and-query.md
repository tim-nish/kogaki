Issue: https://github.com/tim-nish/kogaki/issues/129. On conflict, the issue
and `specs/spec-terrain/SPEC.md` §12 win.

As the Kogaki repository owner, I want every co-tag view to produce a Full
Report — Claims and Glosses untruncated, keyed to the substrate version it was
computed against — so that the screen can stay a compact navigation surface
while the material for thinking a Thesis through lives in a durable,
re-readable artifact.

## Context

`specs/spec-terrain/SPEC.md` §12 is the governing text, authored at v3 to fold
this issue. Its defect specimen is an **absence**: the 2026-08-06 dogfooding
run produced no report artifact anywhere in the flow.

This story is the other half of story 1.29. The screen is compact only because
this artifact exists, which is why `depends_on: 1.29` — the two also share
`terrain/terrain.mjs`, `specs/spec-terrain/SPEC.md` and
`.claude/skills/terrain/SKILL.md`, an overlap accepted and sequenced rather
than split.

The identity rule is the ratified shape for a derivation that outlives its
computation — "acting on it RE-VERIFIES rather than re-resolves … the shared
failure is **silent re-resolution**"
(`consulted: product-lab@f918c5158c718394b3a0e4f10239d75bbb451b74 topics/archive/knowledge-architecture.md:161`)
— and pins rather than a version field carry it
(`topics/articles.md:83@f918c515`).

## Acceptance criteria

- **Given** a co-tag view, **when** the owner pulls its Full Report, **then**
  the report contains the **GroupClaim and every SubGroupClaim in full** and
  the **complete Lesson and Journey Glosses**, with **no truncation anywhere**
  (`specs/spec-terrain/SPEC.md` §12).
- **Given** the same substrate pin and the same co-tag query, **when** the
  report is generated twice, **then** there is **one** report — the rerun is
  idempotent and produces no duplicate (`specs/spec-terrain/SPEC.md` §12.1).
- **Given** the substrate pin advances, **when** the same co-tag query is run
  again, **then** there are **two** reports, one per pin
  (`specs/spec-terrain/SPEC.md` §12.1).
- **Given** one substrate pin, **when** two different co-tag queries are run,
  **then** there are **two** reports, one per query
  (`specs/spec-terrain/SPEC.md` §12.1).
- **Given** a report generated under a pin that has since been superseded,
  **when** it is read, **then** it is **kept as the reading of that pin and
  never silently refreshed onto current content**
  (`specs/spec-terrain/SPEC.md` §12.1).
- **Given** a report is written, **when** its identity is recorded, **then**
  it carries the **substrate pin and the co-tag query** it was computed
  against, with the **served surface authoritative and the report
  subordinate** — the pin is the mismatch check that makes the stored
  derivation admissible (`specs/spec-terrain/SPEC.md` §12.1).
- **Given** a report exists, **when** any downstream artifact is composed,
  **then** **nothing keys on a report id**: Briefs, proposals and
  recommendations cite members and pins, because a Full Report is a rendering
  and not an address (`specs/spec-terrain/SPEC.md` §12;
  `topics/articles.md:64,71@f918c515`).
- **Given** a report is generated, **when** the runtime classifies the act,
  **then** it is written as a **report** — it appears in neither act list,
  ranks nothing and narrows nothing (`specs/spec-terrain/SPEC.md` §2.3, §12).
- **Given** a report is written, **when** its location is chosen, **then** it
  is written to the **machine-local run workspace** (`~/.kogaki/runs/…` or
  `$KOGAKI_RUN_DIR`) and is **never committed**
  (`specs/spec-terrain/SPEC.md` §12.2; `specs/SPEC.md` §4 rider 3;
  `.claude/skills/terrain/SKILL.md` hard lines).
- **Given** a Gloss rendering is missing for a Strand the report covers,
  **when** the report is generated, **then** the absence is **marked as
  ABNORMAL and nothing is substituted for it** — the §9 rule binds the report
  exactly as it binds the screen (`specs/spec-terrain/SPEC.md` §9).
- **Given** the skill's documented flow, **when** it is followed, **then** it
  reaches the Full Report: `.claude/skills/terrain/SKILL.md` names the step
  that pulls one.

## Story questions

- **The report's file format and field names are implementation and are not
  specified here.** §12 binds the content (untruncated), the identity (pin +
  query), the classification (report), and the location (machine-local). It
  binds no schema, on the same ground the hub already ratified for the
  brief — "Field names, file format and emitter are the consumer's and are not
  ratified here" (`topics/articles.md:71@f918c515`).
- **What exactly constitutes "the co-tag query" as a key is
  implementation-decidable but must be stated in the PR** — at minimum the
  selected tag and the named group, since §12.1's third case (two queries, one
  pin, two reports) is what the key has to discriminate.
- **Whether a report is generated eagerly for every co-tag view or pulled on
  demand is not decided here.** The served line describes the owner "pulling a
  Full Report per named group" (`topics/articles.md:79@f918c515`), which
  suggests on-demand; the issue says "every co-tag view produces" one. Both
  satisfy §12's content and identity rules, so the choice is the implementer's
  and is stated in the PR rather than assumed.
