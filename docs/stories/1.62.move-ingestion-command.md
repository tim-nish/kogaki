## Story

As the owner holding a free-form file of self-organized Moves, I want a command
that splits it into records, proposes each in the §4.2 schema, has an agent
review them as judgment, and puts every proposal in front of me on one screen,
so that Moves enter `moves/` by my act rather than by a parser's, and so that a
file whose records silently collapsed is visible to me before anything is saved.

## Context, and what is already settled

§6.9 → §6.9.4 is **merged and ratified** across five PRs (#233, #235, #247, #255,
#259). The design was constructed against the real specimen, not sketched: the
input grammar is measured, the file interior drawn, the filename and INDEX row
derived, and the `move-sources-derivation-vehicle` slot filled. **This story
implements that text and re-opens no fork.** Arm (b) of the file-interior
selection stays declined on §6.9.1's recorded grounds.

The specimen is repository-root `moves.md` — 512 lines, owner-authored,
deliberately untracked and gitignored by PR #393. 22 records, each exactly
§4.2's eight keys in §4.2's order, `status: observed` throughout, zero markdown
constructs, zero excluded draft fields.

## Acceptance criteria

**AC1 — The record boundary is the column-0 `id:` key.**
Given an input file, when the command splits it into records, then a record
begins at a column-0 `id:` key and runs to the next one or to end of file, and
the blank line between records is **not** what the split binds to.
*Grounding:* `specs/spec-draft-pipeline/SPEC.md:625` — §6.9.0 correction 1, and
the record-boundary rule §6.9.0 states below it.

**AC2 — The whole-file parse is refused by name, and the record count is shown.**
Given the specimen, when the command parses it, then it never submits the whole
file to a single YAML parse, and the **parsed record count is displayed at the
selection screen**.
Given a file whose 22 records would collide key-for-key under a whole-file
parse, when the command runs, then the owner sees `22` and not `1`.
*Why this AC is the sharp one:* a whole-file parse **succeeds** and returns one
well-formed mapping — 21 Moves lost with no error, invisible from the parser's
return value. The displayed count is the only instrument that catches it, and it
is arithmetic the command already holds rather than a lint.
*Grounding:* `specs/spec-draft-pipeline/SPEC.md:582` §6.9 and §6.9.0's third
correction.

**AC3 — Markdown is not required, and is refused where the grammar can see it.**
Given an input carrying zero markdown constructs, when the command reads it,
then it locates records without seeking a heading or a fence.
Given a line that condition 4 refuses, when the command reads it, then it
**names the offending line**.
Given a legal column-0 block sequence, when the command reads it, then the `-`
exemption applies and the sequence is not refused.
*Stated residue, inherited and NOT repaired here:* a note bullet among the items
of a legal sequence is indistinguishable from data — bounded to inside a
sequence, only where a prose field was written as one, costing a wrong value
rather than a lost Move.
*Grounding:* `specs/spec-draft-pipeline/SPEC.md:607` §6.9.0 conditions, and PR
#259's `-` exemption.

**AC4 — Normalization is to §4.2's eight fields in §4.2's order, and stripping is conditional.**
Given a record carrying excluded draft fields (`material_roles`,
`compatible_previous/next_moves`, `examples`), when the command normalizes it,
then those fields are stripped.
Given a record carrying none of them, when the command normalizes it, then their
absence is **not** treated as evidence of the wrong file and the record proceeds.
*Grounding:* `specs/spec-draft-pipeline/SPEC.md` §6.9.0 correction 2.

**AC5 — Review is judgment-class, with no verdict machinery and no lint.**
Given a batch of normalized proposals, when review runs, then it applies as
judgment: one transition not an arc, separable from content, an id naming the
operation in established terms, effect differing from requires, statable
invalidity, dedupe against the existing ids, honest `status`, and `sources`
naming real passages.
Given any proposal, when review completes, then `validated` is **never**
assigned as a `status` by this path.
Given a near-duplicate of an existing id, when review completes, then it
proposes a `sources` amendment rather than a new entry.
Given the review output, then **no numeric score, pass/fail verdict, or lint
result** is attached to any proposal.
*Grounding:* `specs/spec-draft-pipeline/SPEC.md:582` §6.9 and `:952` §6.9.2.

**AC6 — One selection screen, and admission is the owner's act.**
Given reviewed proposals, when the command reaches the gate, then it presents
**one** screen offering per-Move accept / decline / free-form.
Given the screen, then nothing is written to `moves/` before the owner's
selection, and **no proposal self-admits** — including one review left
untouched.
Given a review that split or renamed a Move, then what the owner sees is the
reviewed proposal and not the authored record.
*Grounding:* `specs/spec-draft-pipeline/SPEC.md:582` — §6.9's *"ADMISSION IS THE
OWNER'S ACT AT THAT SCREEN, never the command's."*

**AC7 — The saved file's interior, filename and INDEX row are derived, never composed.**
Given an accepted Move, when it is saved, then its body is the §4.2 mapping in
§4.2's order with **no fence and no `---` delimiters**, a paragraph-valued field
written as a `>-` folded scalar.
Given an accepted Move, then its path is `moves/<id>.md` with the `id` as the
whole stem.
Given two accepted Moves sharing an `id`, then the collision surfaces at the
selection screen as review's dedupe judgment and **never as a silent
overwrite**.
Given a completed run, then `moves/INDEX.md` is **rewritten whole** from the
files on disk, sorted by `id`, with columns `id | status | intent`, **every
column read off a file and none composed**.
*Grounding:* `specs/spec-draft-pipeline/SPEC.md:915` §6.9.1a.

**AC8 — The filled slot is executed: the run writes each accepted Move's derivation pointer, as prose provenance.**
Given an accepted Move, when the command saves it, then the derivation pointer
is written **inside `sources`**, in that same act.
Given the saved file, then **no ninth field** has been added to the §4.2 schema.
Given the written pointer, then its form is a **prose provenance line naming the
served ruling**, and **not** a `path:line@sha` pin.
*This executes §6.9.4 and does not re-decide it. The pointer's FORM was the one
thing §6.9.4 left open, and it is decided below rather than embedded silently.*
*Grounding:* `specs/spec-draft-pipeline/SPEC.md:1079` §6.9.4.

## Decisions taken at the bind, with their grounds

**D1 — The AC8 pointer is prose provenance, not a `path:line@sha` pin.**
Owner selection 2026-08-13 at the `/ship-cycle 223` gate. §6.9.4 binds the
*moment* and the *location* and never the *form*; §7.6 forbade `path:line@sha`
in `sources` under a condition §7.6.1 records as **lapsed**, so the prohibition's
standing changed without a successor being selected — a live fork, not a settled
one. The served surface discriminates it:

consulted: product-lab@8906f20752e27d1935c62f24c8ba41ea1d55dba0 topics/knowledge-architecture.md:69

`outcome: discriminating` — 148 unpinned `file:line` citations broke repeatedly,
46 inside append-only blocks where the rot is near-permanent, against 1,127
`#issue` anchors of which every one survived every relocation. Two further
grounds converge: the specimen's 22 records **already** write `sources` this way
(§6.9.0 measured **zero** occurrences of `path:line@sha`), so normalize stays
close to identity; and §7.6's text stays accurate rather than merely lapsed.
**The counter-instance is in this very section** — §6.9.4's own grounding
receipt is a stale pin, per Q1 below.

**D2 — The command lives at `.claude/skills/`.** §6.9 says only *"a kogaki
command"* and names no path, invocation name or argument form. `.claude/skills/`
is the repo's in-tree command home, which makes this **code-class** — an
ordinary branch → PR — rather than an out-of-repo machine-local artifact. A
routine implementation call, stated rather than left implicit. The invocation
name and argument form are the implementer's to choose and to state in the PR.
