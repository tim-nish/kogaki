## Trigger — what happened

specs/spec-terrain/workflow.json v3 recorded that the removed `adopt` subcommand "becomes part of J1_claims' gate re-offer path". No state in that same file's states array rendered a gate, so the destination named nothing. Three review rounds read the map, and the file's own entry_point_accounting asserts that every dispatcher case appears in exactly one of four maps and calls that totality the property. The gap surfaced only when a later sitting (kogaki#666) had to decide where the gate lived and found the answer already written down as if settled.

## The learning

A map from removed things to their replacements is checked for COVERAGE — is every source named? — and almost never for REACHABILITY — does every destination exist? Each entry is well-formed prose read in isolation, and coverage is the property such a map advertises, so a reader who confirms the enumeration is complete has done the check the artifact invites and still learned nothing about whether the destinations are real. The asymmetry is what makes it durable: the source side is a closed set the artifact can enumerate against itself, while the destination side points OUT of the enumeration, at rows in another array or another file, and nothing brings the two together. Worse, a destination written in prose ("J1_claims' gate re-offer path") reads as MORE settled than a bare identifier would, because it describes a mechanism rather than naming a row — so the pointer's specificity substitutes for its truth. Where both sides live in one machine-readable artifact, the cheap remedy is to make the destination an identifier the file can resolve against its own rows, so an unreachable pointer refuses at authoring time instead of being discovered by the sitting that has to build the place it named.
