## A test that could not have failed

This test passed — what would have had to be true for it to fail?

The test in question is an integration test. It covers the code that reads messages from another team's system, and it runs in a few milliseconds because it never talks to that system. Instead it replays a stand-in message the team wrote themselves. Call that stand-in a fixture: the message a test feeds its own code in place of what the real system sends.

Now answer the question. The test would have failed if the reading code mishandled the fixture. It would not have failed if the real system sends something the fixture does not resemble, because the real system never entered the run. So the test proves that the team can read the message they guessed at. Whether they guessed right is a separate question, and the passing test does not touch it.

That is not a general complaint about tests. A test proves something only when there is a real connection between what it runs and the behaviour it claims to cover, and there is a version of this same test that has one. Record a single real message from the live system, save it, and replay that instead. The code under test does not change and neither does the runtime. What changes is that the message is now evidence about the other system rather than a note about what the team expected.

The difference is not academic. When one team did record a real message, the recording showed that the true cause of the failure they were hunting was not on their list of guesses at all — the test had invented its own version of the message, and the invention was wrong in exactly the place that mattered. Every earlier run had passed. Every earlier run had been checking the invention against itself.

So there are two checks here that look identical from the outside. Both are integration tests, both are green, both are in the same suite. One is bound to a message somebody wrote down from belief; the other is bound to a message recorded from the system it claims to cover. Only the second can be contradicted by the world. That is the axis, and it is the one thing worth carrying forward: not whether a check passed, but whether anything it could have observed would have made it report otherwise.

It would be comfortable to file that under fixtures. The lesson would be to record your test inputs, and the rest of the working day would be unaffected. But the fixture is only what made the connection missing in that one case. The relationship that made the test uninformative — nothing it could have observed would have made it report otherwise — is not about tests, and it is easiest to see that by watching the same relationship arrive through three different causes.

Take a cleanup step first. It walks a set of directories, looks for leftover records, and reports what it found. It found nothing, and it said so. The directories it walked, though, were not the directories its records were ever written to. Nothing was there to find, so nothing was found, and the output was indistinguishable from a genuine all-clear. Ask the question of it: what would have had to be true for this to report leftovers? Something would have had to be sitting in a directory the step never wrote to. No state of the actual system produced that. The cause here is a wrong path, not an invented input, and the relationship is the same one.

Take a completeness claim second. A report says it read everything. What it certifies, exactly, is that it read everything on the list of candidates it was given. If a thing never made it onto that list, the report passes without ever having had the chance to miss it, and the passing report and the missing thing coexist without friction. The cause here is a list, not a path and not a fixture. Ask the same question and you get the same answer: no state of the world outside the list could have changed what the report said.

Take an identifier third, and note that this one gets there by a different route again. Two systems on either side of a closed boundary share an identifier to match their records. Neither side can check that the identifier is genuine, because checking it would mean reaching across the boundary for access the design deliberately withholds. So a made-up identifier passes on both sides. Nobody guessed wrong here and nobody misconfigured a path; the checking was foreclosed by the arrangement itself, which is a real difference from the first two cases and worth holding onto. What is not different is the outcome of the question. There is no observation either side is permitted to make that would have rejected the value.

Four cases now: an invented fixture, a wrong path, an incomplete candidate list, a forbidden lookup. Four different underlying conditions, and one relationship running through all of them — the check's output was fixed before the system was consulted, so the system's condition never entered into it. That is a property of checks, not a property of testing. It does not yet say anything about which checks in the world have it; each of these four had to be looked at individually to find out.

## Why nothing contradicts an unfounded answer

The obvious explanation for all four is carelessness, and it is partly right. Somebody did not check which directories the records went to. Somebody accepted a candidate list without asking where it came from. That is real, it is the part of the story a code review is built to catch, and nothing below takes it away.

What carelessness does not explain is how long these stand. Ordinary careless bugs are noisy. They produce a wrong number, and the wrong number disagrees with an invoice or a dashboard or somebody's memory, and the disagreement is what brings it to attention. These four produced no disagreement with anything. So the question the carelessness account leaves open is not why they were written — that part is answered — but why nothing afterwards ran into them.

The missing factor is that these are not wrong answers. They are unfounded ones. An unfounded answer is an answer produced without first establishing that the place it looked exists and is the place it meant. And an unfounded answer has a peculiar property: it agrees with everything. A wrong answer eventually contradicts something, because it makes a claim about the world and the world is around to disagree. An answer computed over nothing makes no claim about the world at all, so there is nothing for the world to push back against. It is not that these evade detection through subtlety. There is nothing to detect against.

The clearest form of that is in the output itself. A cleanup step that read the wrong directories and found no leftovers prints the same thing as one that read the right directories and found no leftovers. Nothing in the output distinguishes computed over nothing from computed and found nothing. A zero is a zero. The report cannot show its own foundation, and no reader of it can supply the missing part by reading harder.

If you want a measure of how ordinary this is rather than how careless anyone was: three of these arrived in a single day. Two were the team's own work. One of them was a verification check — a thing whose entire job is to confirm — that had been approved that morning and that reported a confident zero over records carrying no marker at all. A review had looked at it. The review saw code that computed a zero correctly, which it did.

There is one arrangement where this goes all the way. Follow the completeness claim from earlier into it, and watch each stage.

Start with the list. A checking mechanism keeps a register of the things it knows about, and that register is what a completeness report enumerates. Reading everything means reading everything in the register. So far this is only the general case: the report certifies the list, not the world.

Now choose the failure being hunted. Suppose the worry is that something never got registered at all — that an item exists which the mechanism has no record of. That is a reasonable worry; it is often exactly the worry. But now put it against the list. The report walks the register, finds every entry accounted for, and passes. It would also have passed if ten items were missing from the register, and if a hundred were. The report cannot come out any other way, whatever the answer to the question is.

That is the stage worth naming. Up to here, a check bound to the wrong thing has been weak evidence — it told you something narrow and you read it as something broad. Here it is not weak evidence, it is none. The check cannot be wrong, because nothing it reports bears on the question at all. Its passing and the system being broken are one observation, not two, and no amount of running it more often moves that.

Notice where the ordinary defence was supposed to sit and what happened to it. When somebody hands you a claim about a set of things, the sanity check is to ask what the set is. In this arrangement, the set was supplied by the very person making the claim — the register belongs to the checking machinery. Asking the question produced the list, and the list agreed with the report, because the list was where the report came from. The defence ran, and it ran inside the loop.

The one place a reader could have got in is smaller than that and easier to miss. The incompleteness can be admitted out loud — a comment on the change saying the list may not be exhaustive — and then closed over anyway, because the admission was not attached to anything that could stop the change. That version is catchable in time. It is worth saying that this is one arrangement, with the register and the never-registered failure both required to produce it; a check bound to the wrong list is not always this bad. It is this bad when the list and the question are wired to each other.

## The honest replacement

So what do you write instead? The tempting answer is to write a check for the thing you actually care about. Often you cannot. Some properties do not admit a direct check at all — not because nobody has built one yet, but because deciding them would require an observation nobody is in a position to make. That is the situation the previous section ended in: a question with no check under it, and a green report sitting where a check should be.

The honest move is to give up on checking the property and write down a stricter condition instead — one that a cheap check you already run can actually decide. Stricter means it rules out more than the property does. Everything the condition permits is safe; some things it forbids would have been fine. Call that a conservative proxy: a narrower, decidable stand-in for a property you cannot check directly.

The point of the strictness is that it goes the right way. If the condition holds, the property holds, so a pass is real information. If the condition fails, you do not know that the property fails — you know only that this cheap check cannot clear it, and something has to look. You have not answered the original question. You have converted it into a question that gets answered every time the check runs, and arranged the conversion so the answer you get is never falsely reassuring.

And there is a single test for whether a candidate wording is worth anything, which is the same question the article opened with, pointed at the wording rather than at the run. Ask what observation would decide it. Not who would decide it — what would. If you can name the observation, and the check you already have makes it, the condition is a check. If the answer comes back as somebody's judgement about whether the thing is really a problem, then whatever is on the page reads like a rule and functions as an opinion. The check has quietly been removed, and the wording is the thing that hid the removal.

Run a conservative proxy for a week and you will meet its cost. It fires on things that are fine. Somebody will bring you a case it flagged, walk you through why that particular case is harmless, and ask you to fix the wording so it stops.

Follow what happens if you do. The fix is always the same shape: make the condition say what you really mean. Not this pattern, but this pattern when it is actually dangerous. The reworded version is more accurate — it describes the real concern better than the crude one did. Now put it back through the test from a moment ago and ask what observation decides it. There usually is not one. Whether a given case is actually dangerous is a judgement someone makes, so the rule now reads more precise than before and measures nothing at all. The false alarms disappear, because the check disappeared with them. This is not a slippery slope argument; it is the same mechanism as the earlier cases arriving through a fifth route, and this time you are the one who builds it.

Which means the flagged harmless cases are not a defect in the wording. They are what having a detector costs. A condition strict enough that every pass is real information will forbid things that would have been fine, and the count of those is the price, not the bug. Tune it if the price is too high — that is a real trade you are allowed to make — but tune it knowing you are buying quiet with coverage, and check after each adjustment that some observation still decides the result.

That leaves the residue: the part no decidable condition reaches. The shared identifier from earlier is the clean example. Neither side can verify it, and no rewording changes that, because the verification would need access the boundary exists to withhold. The practice here is not a check. It is a sentence. Keep the identifier if the matching it enables is worth having — often it is — and say plainly, wherever the record is read, that the identifier is unchecked and its presence proves nothing on its own. That intervenes in the mechanism at the only point still open. It does not make the value trustworthy. What it does is stop the value from being read as evidence, which is the specific harm the four cases had in common: not that a check was missing, but that something in the output looked like a check and no one could tell.

So there are three dispositions for a property you care about, and only three. Check it, if a check exists. Replace it with a stricter condition some observation decides, and pay in false alarms. Or carry it unchecked and say so. The failure the whole article has been about is the fourth thing, the one that is not on the list: carrying it unchecked while the report reads green.
